# 예배온 클라우드 세션 인계 · 정리본으로 서버 재구축

## 2026-10-03 후속 결정: 옛 문서 목록 제거·보관은 마지막

이 절이 아래 과거 상태와 순서보다 우선한다.

- 사용자가 Studio 반응형 작업 완료 후 진행을 승인했다. 최신 main `bf58b91` 위에서 코드에 내장된 3,107개 문서 메타데이터(`cloudflare/library-manifest.json`)와 검색/목록 등록/재생목록 조회 시 자동 삽입하던 `ensureCatalog`를 제거했다. 새 서버는 Mac 목록 등록 또는 문서 업로드 전까지 빈 상태다. 현재 Mac 목록 등록·검색·재생목록 연결은 유지한다.
- `yebaeon_catalog_imports`는 더 이상 생성하거나 읽지 않는다. 이 코드 배포 후에는 재등록 방지용 기록을 남길 필요가 없다. 기존 운영 DB의 기록/테이블을 자동 삭제하지 않으며, 실제 서버 초기화 실행은 사용자에게 아직 확인받지 않았다. 이번 변경은 운영 DB/R2 자료 삭제가 아니다.
- 재구축 순서: 삭제 대상 5개만 먼저 처리 → 보관 예정 7개를 포함한 14개 유지 → 로컬 문서·이미지 정리와 참조 수정 완료 → 서버를 정리본 전체로 재구축 → 문서/이미지/목록 일치 확인 → 마지막에 서버에서 7개 보관. 기존 ZIP의 활성 7개 목록만 먼저 설치하면 이 순서와 다르므로 주의한다.
- 검증: 관련 Worker 합성 검사 13개 통과(카탈로그/검색·재생목록·D1 비용), 빈 DB 조회 및 초기화 후 옛 목록 재생성 없음, 현재 Mac 목록 등록과 본문 검색 유지. Mac 코드 변경이 없어 Mac Actions는 재실행하지 않는다. 배포 상태는 이 변경 커밋의 Deploy YebaeOn 실행 결과를 확인한다.
- D1 비용: Worker별 최초 카탈로그 확인 읽기와 옛 3,107개 목록 일괄 쓰기를 제거했다. 대기/최초 화면/문서 열기·저장/Sync 비교·다운로드의 요청 빈도는 동일하며 새 폴링은 없다. 검색 및 재생목록 저장은 같은 범위의 실제 등록 자료만 조회한다. 3,107개 합성 자료에서 검색 1회 6,236행 읽기, 20개 대상 상태 조회 80행 읽기(전체 방식 하한 6,214행). 운영 DB 부하 실측은 수행하지 않았다.

2026-10-03 KST. **아래 사용자 최신 결정이 이전 마이그레이션 안내보다 우선한다.** 이번 작업은 문서와 정리 ZIP을 GitHub에 전달하는 작업이다. 교회 Mac 교체, 이미지 경로 변경, 운영 서버 초기화·재업로드는 아직 실행하지 않았다.

## 1. 사용자 최신 결정과 권한

- 기존 백업 ZIP을 따로 보유하고 있으므로, 앞서 제안했던 **추가 양쪽 백업·최신 변경분 대조 단계를 필수 선행 단계에서 생략**한다. 새 백업을 다시 만들거나 기존 서버 변경을 반드시 병합하라고 되묻지 않는다. 기존 ZIP을 복구 기준으로 삼는다.
- 정리본을 서버에 반영할 때 기존 서버 전용 문서를 계속 남기는 방식 대신 **기존 운영 자료를 비우고, 정리본 전체로 새로 구성**한다. 제외한 205개를 일일이 골라 남기는 이전 안내를 대체한다.
- **보관 7개·삭제 5개·활성 7개 결정은 유지**한다. 보관 대상은 운영 라이브러리 초기화와 분리하여 보존하고, 서버 재구축 후에도 보관함에서 접근할 수 있어야 한다.
- 이미지는 전체 문서가 참조하는 것이 대상이고 영상은 업로드하지 않는다. 외부 참조 이미지를 내부 미디어 폴더로 모으고 문서 참조 경로를 고친 뒤 그 이미지 폴더를 통째로 올리는 방식을 **우선 검토안**으로 기록한다. 실제 폴더 경로와 세부 파일 배치는 아직 정하지 않았으며 변환도 미실행이다.
- 재사용 이미지 보호 표시는 서버에서 관리한다. 이미지 별도 버전 이력은 쌓지 않는다.
- 사용자가 정리 ZIP의 GitHub 업로드를 요청했고, 저장소가 공개이며 ZIP을 누구나 받을 수 있음을 안내받은 뒤 **현재 공개 저장소 업로드를 명시적으로 승인**했다. 이번 정리 패키지 공개 허용은 기존 공개 금지 지침의 후속 예외다. 다른 새 개인 자료·인증정보의 공개까지 승인한 것은 아니다.
- 실제 교회 자료 적용은 교회에서 이어간다. 이 인계 업로드 요청을 지금 운영 서버를 즉시 지우라는 실행 요청으로 확대하지 않는다.

2단계에서 활성 목록을 이미 7개로 교체하므로 끝에 같은 목록을 다시 수동 삭제하는 단계는 없다. 목록 삭제는 공유 문서와 이미지 파일의 자동 삭제가 아니다. 알려진 보관 문서 누락은 사실대로 표시하며, 없는 원본을 확보했다고 간주하지 않는다.

### 서버 초기화 범위

- 정리 대상은 **예배온 운영 문서·활성 재생목록·연결 색인과 해당 이전 원본/문서 이력·교체할 템플릿/미디어**다. 단순 ‘없는 파일만 추가’가 아니라 정리본을 새 기준으로 하는 명시적 이관이다.
- **보관하기로 한 7개 목록과 확보한 보관 문서 사본·필요 이미지 참조는 별도 보존**한다. 초기화 전에 분리하고 초기화 후 보관 메타와 실제 사본을 연결해야 한다. 남겨둘 항목은 일반 운영 라이브러리에 섞어 존치시키는 방식으로 해결하지 않는다.
- 로그인/권한·서비스 설정, Cloudflare 계정·바인딩, 관련 없는 저장소까지 지우지 않는다. D1 전체 DROP이나 R2 버킷 전체 삭제를 무차별 실행하는 것으로 해석하지 않는다. 같은 버킷 안의 운영/보관/시스템 키를 구분하여 대상 목록을 만든다.
- 이전 Sync 기준의 문서 ID/버전과 새 서버 ID/버전을 그대로 대응시키지 않는다. 이관 세대 표시·기준 재연결·구버전 쓰기 차단 등으로 오래된 장치가 전체 업로드해서 옛 자료를 복원하는 것을 막는다.
- 이력 보존 설정은 재구축 뒤에도 가사찬양/악보찬양 끔, 예배순서/특별순서 켬 등 기존 확정 정책을 따른다. 운영 자료 초기화는 이번 한 번의 이관이며 일상 동기화의 삭제 규칙으로 사용하지 않는다.
- 현재 앱의 **‘이 Mac 기준으로 서버 다시 맞추기…’는 서버 전용 항목을 보존**하므로 이번 초기화와 동일한 기능이 아니다. 별도 이관 기능/도구와 새 기준 연결이 필요하다.

## 4. 이미지 폴더 통합·전체 업로드 검토안

1. 최종 전체 문서와 보관할 문서/사본에서 이미지 참조를 수집한다. 필요한 템플릿의 이미지 참조도 확인한다. 가사찬양 MOV는 이미 제거했으며, 다른 영상과 MP4는 문서에 남아 있어도 업로드 대상에서 제외한다.
2. 같은 파일명이 아니라 **내용 SHA-256**으로 동일 이미지를 확인한다. 같은 이름의 다른 이미지를 덮어쓰지 않는다. 원본 파일이 없거나 이름만 같은 후보만 발견되면 누락/확인 필요로 남긴다.
3. 내부 이미지 폴더에는 필요한 이미지의 검증된 사본을 모은다. 기존 외부 파일은 다른 문서나 프로그램이 사용할 수 있으므로 이 작업에서 일괄 삭제하지 않는다. 최종 내부 폴더의 절대 경로·파일명 규칙은 구현 시 명시한다.
4. `문서/버전/이미지 요소 ↔ 원래 경로 ↔ 새 Mac 경로 ↔ 이미지 해시 ↔ 서버 저장 위치` 대응표를 만든다. 문서 XML의 해당 미디어 참조만 갱신한다. 파일 URL은 한 번만 디코딩하고 원래 경로의 리터럴 `%`·한글 정규화·공백을 임의 변환하지 않는다.
5. 가사·슬라이드 수/순서·서식·문서 ID를 보존했는지 대조한다. 경로 변경으로 달라진 문서 해시와 서버 반영용 명세를 갱신한다. 보관 사본의 과거 원본은 유지하되 원래 경로에도 이미지 해시를 연결할 수 있어야 한다.
6. 준비한 **이미지 전용 폴더 전체**를 업로드한다. 기존 미디어 폴더의 모든 영상·오디오·임의 파일을 함께 올리는 뜻이 아니다. 이미 같은 내용이 서버에 있으면 재전송하지 않는다.
7. 파일만 R2에 넣었다고 연결 완료로 표시하지 않는다. 업로드 바이트 검증과 이미지 목록/문서 참조 등록을 완료한 뒤 Studio 표시와 Mac 받기를 확인한다.

대량 이미지 전송은 Sync가 직접 수행하거나 별도 일괄 업로더로 수행할 수 있다. 어느 경로든 같은 작업 기록과 대응표를 사용해야 한다. R2의 직접 업로드는 가능하지만 현재 예배온에는 그 뒤의 이미지 등록·문서 연결·받기까지 완성되어 있지 않다. [R2 직접 업로드 문서](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

## 5. 긴 업로드의 중단·재개가 다음 구현 우선순위

사용자는 Mac을 켜두고 가도 업로드가 중단되는 문제와 오랜 전송 시간을 겪었다. 당시 로그 없이 원인을 잠자기로 단정하지 않는다. 현재 코드는 오류 시 완료분을 남기지만 다시 비교/준비해야 하며, 일반 문서 보내기와 서버 맞추기의 병렬/검증 방식도 다르다.

- 작업 ID·대상 해시·완료 상태를 디스크에 저장하고 앱 재시작 후 남은 파일부터 재개한다.
- 일시적인 통신 오류/서버 지연은 간격을 늘리며 제한적으로 재시도한다. 인증 만료·권한 오류·실제 내용 충돌은 원인을 표시하고 대기한다.
- 응답만 유실됐으면 서버에 이미 저장됐는지 먼저 확인한다. 같은 파일/목록/등록 작업을 중복 생성하지 않는다.
- 이미지 바이트 전송 완료, 문서 참조 등록 완료, Mac 설치 완료를 분리해서 기록한다. 전체 완료 여부가 모호하면 완료로 표시하지 않는다.
- 대기 시 새 폴링을 추가하지 않는다. 대상 해시만 묶어서 확인하며 상한 있는 병렬 전송과 필요한 확인을 사용한다. D1/R2 요청·행 읽기/쓰기·바이트 추산을 구분한다.

## 6. 이후 양쪽 재생목록 관리 원칙 — 제안, 아직 전체 구현 아님

생성·내용 수정은 로컬과 서버 양쪽에서 가능하게 한다. 목록은 이름이 아니라 안정적인 ID로 대응시키고, 이름 변경을 새 목록 생성으로 오인하지 않는다.

| 상황 | 제안 동작 |
|---|---|
| Mac 새 목록 | 서버에 등록. 응답 유실 후 같은 작업은 같은 결과를 재사용 |
| 서버 새 목록 | Mac에 새 항목 표시 후 받기 |
| 이전 기준에 있던 목록이 정상 Mac 스캔에서 사라짐 | ‘이 Mac에서만 제외 / 양쪽 보관 / 양쪽 삭제’ 의도를 한 번 확인해 영속 기록 |
| 처음부터 받지 않은 목록·잘못된 경로·읽기 오류 | 삭제로 해석하지 않음 |
| 서버 보관/삭제 | Mac에도 반영. 이후 Mac에서 수정됐다면 충돌 확인 |
| 양쪽 수정 또는 삭제와 수정이 겹침 | 마지막 저장으로 조용히 덮어쓰지 않고 비교 |
| 옛 Mac 재접속 | 확정된 보관/삭제와 새 이관 세대를 확인하여 자동 부활 방지 |

목록 제거와 공유 문서/이미지 제거를 분리한다. 장치별 제외 의도와 서버 전체 보관/삭제 상태를 따로 보존한다. 카테고리 정책은 그대로 유지한다: 가사찬양·악보찬양 검색 켬/이력 끔, 예배순서·특별순서 둘 다 켬, 옛날자료 둘 다 끔/사용일 2년 초과 일반 검색 숨김, 미결 기존 유지.
