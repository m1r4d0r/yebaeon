- GitHub 비공개 저장소 [m1r4d0r/yebaeon](https://github.com/m1r4d0r/yebaeon)의 `main`에서 앱·배포 파일을 변경하면 GitHub Actions가 검사 후 배포한다. 기존 Cloudflare GitHub 앱 연결은 변경하지 않았다. 실제 문서·미디어의 서비스 저장 위치는 R2로 계획한다. [배포 구성과 검증 기록](../cloudflare/README.md), [전체 Wrangler 설정](../wrangler.jsonc).
- 실제 HTTPS 사이트 응답과 예제 편집·슬라이드 복사·ZIP 저장을 확인했다. 첫 배포와 후속 변경 배포가 모두 성공했다. ZIP의 무결성, XML 파싱, 복사 후 4장 구성을 확인했다. PP6에서의 실제 호환성은 교회 Mac에서 검증한다.
- GitHub 업로드 준비 중 안내용 `sample-demo.js`를 기본 예제로 연결했다. 실제 교회 샘플 `sample-data.js`와 테스트 출력물은 로컬에 보존하고 Git에서 제외한다. 로컬 `web-editor/` 폴더 전체를 공개 정적 파일로 배포하지 않으며, 배포 때 추적 중인 앱 파일만 선별한다. 교회 원본은 로그인 후 접근하는 저장소에 업로드한다.

## 1. 저장 범위

사용자가 명확히 한 요구사항:

- **작업 단위는 플레이리스트**: 서버의 기존 플레이리스트를 열어 찬양 등을 수정·저장하고, Mac에서도 해당 플레이리스트를 선택해 연결 문서와 함께 동기화한다. 단순 파일별 라이브러리는 보조 기능이다.

- **모든 `.pro6` 문서 업로드**: 집에서도 교회 전체 문서 라이브러리를 열고 편집한다.
- **성경 자료 업로드**: 원본을 보관하고, 형식 확인 후 본문 조회·검색·슬라이드 생성에 연결한다.
- **실제로 사용된 미디어 업로드**: 문서가 참조하는 이미지·영상·오디오를 연결한다. 미사용 미디어 전체를 무조건 올리는 계획은 아니다.
- 웹 편집기는 미디어 교체, 슬라이드 추가·정렬까지 포함한다.
- 집 Windows와 교회 High Sierra를 오가며 사용한다. 교회 PP6는 로컬 파일로 운영한다.

기존 `NEXT-STAGE.md`의 “서버에 media를 저장할 필요가 없다”, “서버는 package 전달만”이라는 범위는 이 요구사항을 반영하지 못했다. 해당 내용을 수정했다. 서버의 역할은 **공유 문서 라이브러리·성경 자료·사용 미디어 보관, 편집본 버전 관리와 동기화**다. 로컬 ZIP 전달도 계속 지원한다.

세부 확인 중:

1. **사용 미디어의 기준**: 모든 업로드 문서의 참조인지, 현재 기본 재생목록의 참조인지 사용자에게 질문한 상태다. 답변 전 설계 가정은 모든 업로드 `.pro6`의 참조이며, 초기 전송은 재생목록에서 쓰는 파일부터 시작할 수 있다. 이는 확정된 선택이 아니다.
2. **성경 원본의 형식·번역본·크기**: 현재 첨부 목록에서 본문 데이터는 확인하지 못했다. 원본 저장과 웹에서 검색 가능한 형태로 가져오기는 별도 작업이다. PP6 전용 모듈을 바로 해석할 수 있다고 가정하지 않는다.

|---|---:|---:|---:|

| Renewed Vision Media 전체 | 10,393 | 5,366,707,243 | 5.37GB |

미디어 합계에는 미사용 파일, 다른 경로의 동일 내용, 폴더 아이콘 등도 들어 있다. 실제 필요 용량이나 전체 참조 미디어의 상한으로 볼 수 없다. 관리 폴더 밖의 참조 파일도 있을 수 있다. Documents 목록은 전체 3,103항목 중 `.pro6`만 집계했다. ProCG 목록의 `Icon` 파일명에 줄바꿈 문자가 있어 2행이 0바이트 항목 하나를 나타낸다.

ProCG 목록에는 200,000,000바이트 초과 파일이 21개 있으며 최대 약 339MB다. 현재 웹 편집기의 새 미디어 200MB/총 500MB 제한과 메모리 기반 ZIP은 전체 라이브러리 전송 방식으로 사용할 수 없다. 전용 업로드 대기열과 분할 전송이 필요하다.

사용 미디어 용량 확정 절차: 문서·재생목록에서 참조 수집 → 실제 경로 해결 → 모호함/누락 표시 → SHA-256으로 내용 중복 제거 → 업로드 대상과 크기 합산. 아직 전체 참조 분석 결과는 없다.

## 3. 호스팅 비교 및 추천

**추천: Cloudflare Workers + Static Assets + R2 Standard + D1.** 사용자가 Netlify와 Cloudflare를 모두 사용해 봤으며, 이미지·영상을 여러 장소에서 열고 받는 서비스여서 파일 전송 비용과 관리 구성을 우선한다.

| 선택 | 평가 |
|---|---|
| Cloudflare에 편집기·API·자료 저장을 함께 구성 | 추천. R2 파일 저장과 D1 목록/버전 관리를 연결하고 한 서비스 계정에서 운영할 수 있다. |
| Netlify 편집기 + Cloudflare R2/API | 가능. Netlify 배포 흐름을 유지하고 싶을 때 대안. 인증·배포·CORS를 두 서비스에 맞춰 관리해야 한다. 미디어를 R2에서 직접 받도록 구성한다. |
| Netlify + Functions + Blobs/Database | 가능. Blobs는 파일당 최대 5GB를 지원한다. Netlify가 전달하는 파일·영상 다운로드는 전송량 크레딧에 포함되므로 사용량과 기존 계정 플랜 확인이 필요하다. |

Netlify도 파일 저장이 가능하다. 다만 이 프로젝트에서는 R2의 다운로드 전송료가 없다는 점을 선택 근거로 삼는다. [Netlify Blobs](https://docs.netlify.com/build/data-and-storage/netlify-blobs/), [Netlify 전송량 과금](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/).

2026-09-28 확인한 공개 요금:

- **R2 Standard**: 월 10GB-month 저장, 쓰기 계열 100만 회, 읽기 계열 1,000만 회 무료. 초과 저장은 $0.015/GB-month이며 R2에서 나가는 전송료는 없다. 요청 수 초과 과금은 별도다. [공식 요금](https://developers.cloudflare.com/r2/pricing/)
- **Workers**: 무료 플랜으로 시작할 수 있고 유료 플랜은 월 최소 $5. 실제 API 사용량에 따라 추가 과금한다. 정적 편집기 파일만 제공하는 요청은 무료이며, API/인증 코드를 실행하는 요청과 구분된다. [Workers 요금](https://developers.cloudflare.com/workers/platform/pricing/), [정적 파일 과금](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)
- **D1**: 무료 플랜은 계정 합계 5GB, 하루 읽기 500만 행·쓰기 10만 행 포함. 단일 DB 크기 등 별도 한도가 있으므로 초기 가져오기를 나누고 검색에 색인을 둔다. [D1 요금](https://developers.cloudflare.com/d1/platform/pricing/)
- **Netlify 현행 크레딧 플랜**: Free 월 300크레딧, Personal $9/1,000크레딧, Pro 기본 $20/3,000크레딧. 전송량은 1GB당 20크레딧이며 배포·요청·연산도 같은 예산을 사용한다. 2025-09-04 이전 계정은 기존 플랜을 유지할 수 있어 사용자 계정의 실제 조건은 별도 확인한다. [요금표](https://www.netlify.com/pricing/)

R2 저장료만 계산하면 월 내내 10GB는 $0, 50GB는 약 $0.60, 100GB는 약 $1.35다. 무료 저장 할당량을 이 프로젝트에서 전부 사용할 수 있다고 가정한 값이다. API·요청 초과·DB·도메인·세금·환율은 별도이며, 보관한 이전 버전과 미리보기 파일도 저장량에 포함된다. R2는 무료 사용량이 있어도 사용 시작 시 구독/결제 설정을 거친다. [R2 시작 안내](https://developers.cloudflare.com/r2/get-started/)

### 추가 비교: 다른 서비스와 계정 분리

사용자는 Cloudflare에서 사이트 두 개를 운영 중이며, 이번 프로젝트는 다른 계정으로 만들 생각이라고 밝혔다. 익숙한 서비스에 한정하지 않고 대안을 비교해도 된다는 요청에 따라 다음을 검토했고, 이후 Cloudflare를 선택해 위 진행 기록대로 배포했다.

| 대안 | 이 프로젝트에서의 판단 |
|---|---|
| Supabase + 정적 편집기 호스팅 | 가장 유력한 대안. 로그인·Postgres DB·파일 저장·접근 제어를 함께 제공해 계정/데이터 기능을 연결하기 편하다. Free는 파일 저장 1GB, 파일당 50MB 제한, 1주 비활동 시 일시 중지가 있어 영상 라이브러리의 장기 운영은 제약이 있다. Pro는 월 $25부터, 파일 저장 100GB와 일반/캐시 전송량 각 250GB를 포함한다. 포함량·프로젝트 연산 규모 초과 비용은 별도다. 편집기 화면은 Cloudflare/Netlify 같은 정적 호스팅에 둔다. |
| Firebase | 로그인·DB·파일 저장·웹 호스팅이 마련되어 있는 대안. Cloud Storage를 사용하려면 Blaze 종량제와 결제 계정이 필요하고, 저장/전송/DB의 각 사용량을 따져야 한다. 현재 규모에서는 파일 전송료가 없는 R2를 우선 추천한다. |

출처: [Supabase 요금과 기능](https://supabase.com/pricing), [Firebase 요금](https://firebase.google.com/pricing), [Firebase Storage 결제 플랜 요구사항](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024). 2026-09-28 확인.

추천은 Cloudflare를 유지한다. 파일 보관·전송 비용을 낮게 유지하고 로컬 PP6와 연결하는 현재 요구에 맞는다. 로그인·권한·관계형 데이터 기능을 더 빠르게 구성하는 편의와 월 $25 이상의 운영비를 교환할 수 있다면 Supabase가 좋은 대안이다. Cloudflare 구성에서는 로그인/권한 관리 방식을 별도로 선택해 연결해야 한다.

사이트 두 개가 있다는 이유로 계정이 가득 찬 것은 아니다. Cloudflare는 계정당 Pages 100개, Workers Free 100개를 지원한다. 다만 Workers Free의 하루 100,000회 요청 한도는 계정 단위이므로 기존 프로젝트 사용량도 고려해야 한다. [Pages 한도](https://developers.cloudflare.com/pages/platform/limits/), [Workers 한도](https://developers.cloudflare.com/workers/platform/limits/).

같은 계정에 PP6 전용 Worker/R2 저장소/D1 DB를 만들 수 있다. 교회 자료의 소유권·결제·관리 권한을 기존 사이트와 분리하려는 목적이면 별도 계정도 합리적이다. 기존 두 사이트의 실제 서비스 구성·사용량은 확인하지 않았으므로 영향이 전혀 없다고 보장하지 않는다.

## 4. 자료별 저장 방식

| 자료 | 제안한 보관/처리 |
|---|---|
| 편집기 HTML/CSS/JavaScript | Workers Static Assets에 배포 완료. GitHub Actions로 갱신한다. |
| `.pro6` 원본과 편집 버전 | R2에 원본 bytes를 보존. D1에 제목·상대경로·버전·본문 검색용 정보·현재 버전 포인터를 둔다. |
| 이미지·영상·오디오 | R2에 저장. 파일명과 원래 Mac 경로는 별도 메타데이터로 보존하고, 내용 hash로 중복을 줄인다. |
| 성경 자료 | R2에 원본 보관. 형식 확인 후 번역본/권/장/절을 기준으로 D1 또는 장별 데이터로 가져온다. 검색·구절 선택·슬라이드 생성은 별도 구현한다. |
| 재생목록 | 최우선 구현. `.pro6pl` 원본/버전과 파일 안의 플레이리스트·순서·문서 연결을 보관한다. 참조 문서 버전도 동기화 대상에 포함한다. |
| 템플릿 | 원본 보관 및 편집 지원 범위를 별도로 정한다. |
| 썸네일·영상 포스터·웹 미리보기 | 원본과 구분한 파생 파일로 R2에 보관. 브라우저에서 못 읽는 MOV/PSD도 원본 업로드를 막지 않고 미리보기 미지원으로 표시한다. 필요한 변환은 별도 작업이다. |
| 교회 적용 이력 | 문서별 마지막 적용 버전과 hash를 기록. 웹의 최신 편집본과 교회에서 실제 적용된 버전을 구분한다. |

문서·미디어 원본은 입장한 사용자만 접근하는 저장소에 둔다. 현재 `.pro6`는 세션을 확인하는 Worker API로 읽고 쓴다. 큰 미디어에는 짧은 유효기간의 전송 주소를 검토하며, 브라우저·Mac에 저장소 전체 접근키를 넣지 않는다. [R2 임시 접근 URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

큰 파일은 진행률·재시도·이어올리기를 제공하는 분할 업로드로 처리한다. 문서 저장은 기대한 이전 버전과 일치할 때 새 버전을 확정해, 두 PC의 변경을 조용히 덮어쓰지 않도록 한다. 모든 3,102개 문서의 슬라이드/썸네일을 한꺼번에 열지 않고 목록을 나누어 읽으며 선택한 문서를 렌더한다. [R2 업로드 방식](https://developers.cloudflare.com/r2/objects/upload-objects/)

파일 전송 무결성과 중복 판정에는 원본 SHA-256을 쓴다. 현재 Core의 semantic fingerprint에는 RTF 서식 누락 문제가 있으므로 서버 버전의 유일한 변경 판정 기준으로 쓰지 않는다.

## 5. 집과 교회의 역할

- **집 Windows**: 클라우드 문서 목록/성경 조회, 웹 편집, 미디어 업로드, 새 버전 저장, 변경분 준비. 서버 연결 및 이 기능들은 Mac 검증을 기다리지 않고 개발할 수 있다.
- **교회 High Sierra**: 전체 원본과 필요한 미디어의 최초 수집·업로드, 이후 변경분 전송/수신, 로컬 비교, PP6 종료 확인, 백업·적용·복원. 초기 자료를 집으로 가져와 업로드하는 방법도 지원한다.
- 교회 앱은 HTTPS API와 파일 전송을 사용하도록 설계한다. High Sierra에서 최신 웹 편집기나 서버 개발 도구가 실행된다는 전제로 만들지 않는다. 실제 Mac의 TLS/인증·한글 경로·큰 파일 수신/재시도는 현장 검증 항목이다.
- 서버의 `.pro6` 원본 경로를 웹 미리보기 때문에 전부 바꾸지 않는다. 웹에서는 참조와 업로드 자산의 대응표로 읽고, PP6용 새 미디어 경로 변환은 Mac 적용 시 처리한다.
- 교회에서 수정한 문서도 새 버전으로 올릴 수 있게 한다. 웹과 Mac 모두 같은 기준 버전에서 변경했다면 충돌을 표시한다.
- 교회가 이미 받은 문서·미디어로 PP6를 실행하는 데 서버 연결이 필수여서는 안 된다. 인터넷이 없을 때는 로컬 운영과 업데이트 ZIP 전달을 유지한다. 초기 동기화는 문서/미디어를 자동 삭제하지 않는다.

서버가 생겨도 PP6와 웹의 글꼴·줄바꿈 차이가 자동 해결되지는 않는다. 웹 근사 렌더 개선과 교회 실기 대조는 계속 별도로 진행한다.

## 6. 다음 구현 순서

2026-10-01 사용자 확인에 따라 플레이리스트 중심으로 순서를 수정했다. 문서 단위 저장·송수신은 재사용하는 기반이며 최종 사용자 흐름이 아니다.

1. **최우선:** 서버에 기존 `.pro6pl` 원본/버전과 플레이리스트별 순서·문서 참조를 등록한다. 이미 구현한 `.pro6` 저장소와 연결하고 누락/중복을 표시한다.
2. **웹:** 플레이리스트 목록 → 찬양/말씀 선택 → 기존 편집기 → 저장 → 플레이리스트로 돌아오는 흐름을 연결한다. 전체 문서 라이브러리는 보조로 둔다.
3. **Mac:** 플레이리스트를 고르면 연결된 문서 변경까지 묶어 비교·수신·백업·적용한다. 재생목록 구조가 바뀌지 않은 가사 수정도 감지해야 한다. 선택하지 않은 재생목록과 기존 파일은 보존한다.
4. **교회:** 실제 플레이리스트 하나에서 웹 편집 → Mac 동기화 → PP6 열기/저장을 확인한다. 한글 경로·공유 문서·누락·충돌·중단 복구도 검사한다.
5. **이후:** 사용 미디어 서버 저장·설치·경로 변환, 성경 원본과 검색·슬라이드 생성.

자세한 기준은 [플레이리스트 작업 흐름](PLAYLIST-WORKFLOW.md)을 따른다. 미디어 전체 전송이나 썸네일의 완전한 일치는 첫 플레이리스트/문서 연결의 선행 조건으로 두지 않는다.
