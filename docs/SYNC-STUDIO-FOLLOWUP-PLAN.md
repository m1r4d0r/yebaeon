## 작업 묶음 0 · 서버 현황 페이지와 DB 조회 절감

### 코드 확인 결과와 비용 해석

- D1의 500만 행 읽기는 Workers Free **하루 한도**다. 한국 시간 오전 9시(00:00 UTC)에 재설정된다. 화면에 반환한 행 수가 아니라 SQL 실행 시 스캔한 행(인덱스 포함)이 기준이다. 색인/테이블 변경이나 저장도 SQL에 따라 읽기가 함께 발생할 수 있다.
- GitHub 문서 읽기·소스 수정·푸시 자체는 운영 D1 조회가 아니다. 로컬/CI 모사 검사는 운영 DB와 분리된다. 배포 후 접속·실제 저장/업로드·목록/검색·스케줄 작업은 운영 DB를 사용한다.
- web-editor/status.js: 보이는 탭에서 10초마다 /api/status. 숨긴 탭은 refresh에서 건너뛰지만 다시 보이면 즉시 조회한다.
- cloudflare/status.mjs: 문서 COUNT/SUM/MAX, 이전 버전 JOIN 집계, 최근 12개 정렬, 작업자별 GROUP BY 등 7개 쿼리를 반복한다. 화면에서 사용하지 않는 workers 집계도 계산한다. 예시로 문서 3천 행 집계 하나만 10초마다 반복해도 1시간 약 108만 행 스캔 규모이며 여러 집계/JOIN이 더해진다. 실제 요청별 rows_read는 아직 측정하지 않았다.
- wrangler.jsonc의 매분 cron → worker.mjs scheduled → indexUsage(32)·indexSearch(16). 색인 미완료 대상 찾기와 전체 진행 집계가 완료 이후에도 실행된다. 브라우저를 닫아도 발생한다.
- web-editor/cloud.js의 상태등 30초 갱신 → sync-observations.mjs GET에서 전체 문서 해시·전체 상태 보고를 읽고 서버 재생목록도 R2에서 파싱한다. 문서 검색 시에도 상태등 refresh가 호출된다.
- library-catalog.mjs의 이름/본문 검색은 instr를 이용한 부분 문자열 비교이며 일반 SQL 인덱스로 검색어를 바로 찾는 구조가 아니다. 목록 요청마다 searchProgress 전체 집계도 있다. ‘본문 색인을 만들었다’는 것은 원본 XML을 검색마다 다운로드하지 않는다는 뜻이며 D1 스캔 비용이 없어졌다는 뜻은 아니다.
- 알림의 94% 약 470만 행 중 각 경로의 실제 비중은 미확정이다. 현황판만 원인이라고 단정하지 않는다. 운영 쿼리별 메타/Cloudflare Metrics 확인 전 합계 추정을 실제 측정으로 기록하지 않는다.

공식 근거: https://developers.cloudflare.com/d1/platform/pricing/ 및 https://developers.cloudflare.com/d1/observability/metrics-analytics/ (2026-10-02 확인). 무료 한도 소진 시 D1 쿼리가 실패할 수 있으므로 반복 조회부터 줄인다.

**목표:** 무엇이 바뀌었고 왜 받을 수 있는지/없는지를 정확히 설명한다.

- [ ] 최초 원본 등록 경로에서 예배별 동기화 기준이 빠지는지 재현하고, 원본 파일 등록과 예배 노드 기준 초기화를 일관되게 처리한다. 기준이 없는 상태를 임의로 ‘같음’으로 단정하지 않는다.
- [ ] 문서 본문 비교와 재생목록 구성 비교를 분리한다. ‘순서에 추가’, ‘순서에서 제거’, ‘본문 변경’, ‘순서 이동’, ‘변경 없음’을 표현하며 한 항목에 여러 변경이 함께 있으면 함께 표시한다.
- [ ] 새로 추가된 문서의 본문이 로컬과 같아도 ‘그대로’만 표시하지 않는다. 제거는 재생목록 참조 제거이며 파일 삭제가 아님을 유지한다.
- [ ] XML 비교 기준을 Studio와 Sync에서 확인한다. 경로 재작성·사용 기록 등 의미 없는 차이를 줄일 후보를 구분하되 PP6에 중요한 속성까지 일괄 무시하지 않는다. 원본 무결성 SHA-256과 의미 비교용 기준의 역할을 구분한다.
- [ ] 선택 예배의 준비 상태, 충돌/기준 없음, 연결 문서 변경, 받기 버튼 활성 상태, 서버 상태 보고가 같은 판단을 사용하도록 한다.
- [ ] 상태등은 좁은 폭에 맞는 작은 램프와 툴팁으로 유지한다. 초록=마지막 확인에서 일치, 노랑=서버 변경/받기 필요, 파랑=Mac 변경/보내기 필요, 빨강=양쪽 변경, 회색=미확인/미업로드. 판단 불가는 설명을 동반하고 일치로 보고하지 않는다.
- [ ] 여러 Mac의 과거 보고가 섞일 때 장치·확인 시각·판정 근거를 확인할 수 있게 한다. 마지막 관측 상태이지 실시간 Mac 감시가 아님을 표시한다.
- [ ] 금요예배에서 새 곡 추가·기존 곡 제거·말씀 본문 변경을 시험 폴더로 수신하고 로컬 XML/문서 실제 반영을 확인한다. 다른 예배 보존과 공유 문서 1회 수신도 확인한다.

**완료 조건:** 추가/제거/본문만 변경/순서만 변경/일치/최초 기준 없음/양쪽 변경 사례가 비교표·버튼·상태등에서 모순 없이 나타난다. 독립 예배 동시 저장은 성공하고 같은 예배 동시 변경은 차단된다. 백업과 중단 복구 검사를 통과한다. PP6 실제 재열기는 별도 실기 기록한다.

## 작업 묶음 3 · 시작 점검·인덱스·본문 색인·완료 상태

**목표:** 실행 직후 필요한 비교를 빠르게 수행하고 작업 완료 후 정상 종료한다.

- [ ] 시작 흐름 ‘인덱스 갱신 → 문서 변경 비교 → 예배별 재생목록 비교’를 유지하고 단계별 시간·처리 개수를 측정한다.
- [ ] 문서 전체 원본 읽기·해시·XML 분석의 반복을 줄인다. 비교 회차 공유 캐시와 유효한 로컬 캐시를 검토하되 송수신 직전 변경 확인을 유지한다.
- [ ] inventory는 경로·크기 등 목록 갱신에 필요한 데이터부터 처리한다. 새 문서는 즉시 이름 검색·참조 추가가 가능하고 원본 없으면 편집 불가로 나타나야 한다.
- [ ] 본문 색인은 서버에 업로드된 최신 원본을 점진 처리한다. 전체 본문 추출을 시작 점검의 필수 대기로 묶지 않는다. 미업로드 원본의 본문은 검색할 수 없음을 유지한다.
- [ ] 진행 상태를 ‘목록 확인/비교/전송/마무리/완료/실패’로 구분하고 마지막 비교와 마지막 성공 전송 시각을 구분한다.
- [ ] 업로드 완료 뒤 잠금·종료 차단이 남지 않는지 build 12 이후 실제 흐름을 재검증한다. 선택적 상태 보고 실패가 완료 작업을 무한 대기시키지 않게 한다.

**완료 조건:** 변경 없는 재실행과 소수 변경 사례의 시간·파일 읽기 수를 전후 비교한다. 인덱스 실패 시 기존 목록 유지, 원본 업로드 후 참조 연결, 새 버전 본문 검색, 전송 완료 시 busy 해제·종료를 확인한다. 교회 대용량 실측은 별도 기록한다.

## 작업 묶음 4 · 브라우저 초안 자동저장과 명시적 서버 저장

**목표:** 순서를 편집할 때 기다림 없이 초안을 보존하고 저장 버튼으로 서버에 반영한다.

- [ ] 순서 추가·삭제·이동·교체는 브라우저 초안 자동저장으로 처리하고 편집마다 서버 PATCH를 보내지 않는다.
- [ ] 재생목록 순서를 명시적으로 서버에 저장하는 버튼의 대상과 동작을 분명히 한다. 기존 문서 저장 버튼이 순서까지 저장하는 것처럼 보이지 않게 한다.
- [ ] 초안 저장 상태·서버 미저장 상태·서버 저장 성공·충돌·실패를 구분한다.
- [ ] 서버 저장 성공 시 왼쪽 목록과 현재 화면의 ‘저장 안됨’ 표시를 즉시 갱신한다. 문서를 다른 곳으로 갔다 돌아와야 사라지는 현상을 재현하여 확인한다.
- [ ] 저장 실패·동시 편집 충돌 시 초안을 유지한다. 새로고침과 문서/예배 전환 뒤 초안 복원을 확인한다.
- [ ] 예배별 노드 CAS와 이력을 유지하여 다른 브라우저의 1부·2부·3부 작업이 금요예배 저장과 충돌하지 않도록 한다.

**완료 조건:** 여러 순서 편집 중 서버 저장 요청 0회, 저장 버튼 클릭 시 요청 발생을 확인한다. 새로고침 초안 복구, 저장 성공 즉시 표시 갱신, 같은 예배 충돌 시 초안 보존, 다른 예배 저장 병존을 브라우저 검사로 확인한다.

**이전 저장 오류 취급:** 사용자는 첫 저장 실패를 우선 일시적 문제로 보기로 했다. 코드 갱신 때문이라는 원인은 미확정이다. 별도 대규모 원인 조사로 확대하지 않으며 재현되면 요청 오류와 로그를 확보한다. 저장 성공 뒤 목록 표시가 늦게 갱신되는 현상은 별도 검증 항목이다.

## 작업 묶음 5 · 예배별 이력·묶음 싱크·복구 최종 확인

**목표:** 예배별 작업을 독립 보관하고 싱크할 때 안전하게 묶어 적용한다.

- [ ] 이미 구현한 예배별 서버 이력이 실제 금요예배/각 부 예배에 독립 기록되는지 확인한다.
- [ ] 백업/복구 기록은 하나의 싱크 작업 묶음과 그 안의 예배·문서 상세를 구분한다. 서버 순서 이력과 로컬 적용 백업을 같은 개념으로 표시하지 않는다.
- [ ] 여러 변경 예배를 한 번 받을 때 공유 문서를 중복 수신하지 않고 선택하지 않은 예배를 보존하는지 확인한다.
- [ ] 충돌/누락/기준 불명 항목의 제외 이유와 완료/미완료를 확인한다. 완료된 받기 10회 보관과 중단 기록 보호를 유지한다.
- [ ] 단계 중단·복구 후 예배별 기준과 문서 기준·상태등도 일관되게 돌아오는지 확인한다.

**완료 조건:** 독립 예배 동시 저장 → 묶음 비교 → 백업 → 문서/순서 적용 → 재비교 → 중단 복구를 연동 검사한다. 실제 PP6 수용 여부와 화면은 교회에서 별도 확인한다.

## P0 구현 기록 · 2026-10-02

- 매분 cron과 scheduled handler 제거: 브라우저가 닫힌 상태에서 자동 색인 전체 점검은 실행하지 않는다. 신규 저장·업로드 시 본문/사용일 즉시 색인은 유지한다. 기존 본문은 Studio가 남은 대상을 8개씩 처리하며 사용일은 최근 사용순 목록의 기존 점진 수집을 유지한다. 완료 여부를 매분 확인하는 별도 작업은 없다.
- 현황판의 10초/탭 복귀 자동 조회 제거. 최초/로그인 완료/새로고침 때만 조회한다. 이전 버전 용량은 ‘용량 상세 확인’ 버튼에서만 집계한다. 초기 업로드 남은 예상 수는 이름 인덱스/원본 미업로드 수로 대체한다.
- Studio 상태등의 30초 전체 조회 제거. 목록/재생목록 갱신과 저장 완료 시 조회한다. 다른 사용자의 변경은 다음 명시적 갱신 때 표시될 수 있으며 상태등은 마지막 Mac 보고 기준이다.
- 현황 SQL의 미사용 작업자 집계 제거, 최근 저장/Sync 기록 정렬 인덱스 추가. 현황 쿼리별 rows_read/rows_written만 로그에 남긴다. 문서명/내용/세션은 로그에 추가하지 않는다.
- 현재 목록의 부분 문자열 검색과 수동 진행률 집계는 남아 있다. 일반 인덱스로 부분 문자열 검색 비용이 없어졌다고 주장하지 않는다. 추가 검색 최적화는 비용 관측 후 별도 작업이다.
- 최초 로컬 47개 실행은 체크아웃에 dummy_old.xml fixture가 없어 1개 실패했다. GitHub의 원본 fixture를 확보한 후 47개 통과. 기능/보호 검사 완화 없음.
- 운영 계정 Metrics에 직접 접근하지 않았으므로 실제 470만 행의 구성·절감률은 미확정이다. cron 제거 후 자동 호출 0회, 화면 유휴 조회 0회는 설정/브라우저 검사로 확인하며 운영 비용은 로그와 Cloudflare Metrics로 후속 관측한다.
- 상태: CI·배포 확인 전. P1~P3은 다음 묶음 작업이며 아직 시작하지 않았다.
