# 작업 규칙

세션마다 지키는 보고·승인·Actions·공개 저장소·문서 규칙. 먼저 [STATUS](../STATUS.md)와 [BACKLOG](../BACKLOG.md)를 읽는다.

## 보고

- 사용자에게 한국어로 보고한다.
- 오류나 GitHub 검사·배포 실패가 있었다면 증상과 실패 단계, 확인한 원인, 해결 방법, 재검증 결과, 현재 중단 여부와 미완료 항목을 최종 보고에 넣는다. 확정하지 못한 원인은 추정으로 구분한다.
- 실패 실행과 수정 후 성공 실행을 연결한다. 실행 중인 검사를 성공으로 표시하지 않는다.
- 검사 실패, 배포 실패, 교회 Mac의 실제 업로드 중단을 구별한다.
- 오류가 없으면 관련 검사·배포의 성공 또는 대기 상태만 짧게 보고한다.

## 승인이 필요한 일

- main 병합, 운영 배포, 운영 데이터 변경은 사용자의 명시 승인 뒤에만 한다.
- 자동 검사는 로컬 Worker 모사만 쓴다. 운영 D1을 치지 않는다.

## GitHub Actions

- 무료분도 운영 비용으로 취급한다.
- 로컬에서 가능한 JS·Worker·정적 검사를 먼저 하고, 작은 수정마다 원격 Mac 검사를 돌리지 않는다.
- Mac 네이티브 빌드·GUI·호환성 검사는 main의 `[verify-mac]` 커밋이나 수동 실행에서만, 변경을 묶은 후보에 쓴다. 실패 수정 후 필요한 재검증은 하되 같은 코드의 중복 검사와 캡처만을 위한 재실행은 피한다.
- 성공 실행의 설치 파일과 캡처를 재사용한다. 검증한 커밋과 배포 대상 사이에 앱 관련 변경이 없음을 확인하고, 미검증 변경을 검증 완료로 보고하지 않는다.
- 최신 macOS CI 결과를 교회 High Sierra 실기 검증으로 표현하지 않는다.
- 실행 전 저장소가 공개 상태인지 확인하고, workflow에도 공개 조건을 둔다.
- Mac 자동 실행 조건을 추가하거나 검사 빈도를 높이기 전에 예상 사용량과 이유를 사용자에게 설명한다.
- 계정 유료 결제, 지출 한도, 저장소 공개 여부를 임의로 바꾸지 않는다.
- 데스크톱 세션 사용 여부를 사용자의 비용 책임으로 돌리지 않는다. 네이티브 Mac 검사에는 적합한 macOS 도구 환경이 필요하며, 일반 검사까지 Mac에서 반복할 필요는 없다.
- 검사는 교회 PP6를 종료시키지 않고 합성 자료로 한다.
- 검사 개수를 버전마다 늘리지 않는다. 변경의 실패 위험을 검증하는 기존 범위부터 고르고, 데이터 전수 대조를 상시 회귀 검사로 복제하지 않는다.

## 공개 저장소

- 교회 원본, 진단 자료, 정리 패키지, 인증 정보를 새로 커밋하지 않는다.
- 사용자 원본 파일명과 경로를 임의로 정리하거나 바꾸지 않는다.

## 문서

- 세션마다 새 인계 파일을 만들지 않고 STATUS를 덮어쓴다.
- 끝난 일은 CHANGELOG에 한 줄로 적는다. 배포 커밋에 함께 넣는다. 빌드가 CHANGELOG 마지막 5줄을 Studio 개발자도구 콘솔에 배포 번호(Actions run 번호)·커밋과 함께 보여 준다(`build-info.js`).
- 남은 일은 BACKLOG 한 곳에서만 관리하고, 끝나면 CHANGELOG로 옮기며 BACKLOG에서 지운다.
- 상세 경위는 archive에 둔다.
