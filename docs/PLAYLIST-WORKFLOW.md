# 플레이리스트 중심 작업 흐름 · 2026-10-01

## 확정된 사용자 목표

서버에 등록한 기존 플레이리스트 선택 → 안의 찬양·말씀 문서 편집 → 저장 → 교회 Mac에서 해당 플레이리스트 동기화 → PP6의 같은 플레이리스트에서 확인.

사용자가 고르는 작업 단위는 플레이리스트다. `.pro6`는 그 안에서 참조하는 문서 저장 단위다. 문서별 버전 관리와 동기화 엔진은 유지하되, 사용자가 매번 바뀐 문서를 찾아 체크하는 흐름을 최종 제품으로 삼지 않는다. 미디어 전체 전송을 기다리지 않고 기존 경로를 유지하는 플레이리스트/문서 동기화부터 연결한다.

## 코드 점검 결과

| 단계 | 현재 상태 | 빠진 연결 |
|---|---|---|
| 서버 플레이리스트 등록·목록 | 미구현 | `.pro6pl` 원본·버전, 안의 플레이리스트와 순서 항목 목록 |
| 웹에서 플레이리스트 열기 | 미구현 | 플레이리스트 목록 → 찬양/말씀 순서 → 기존 문서 편집기 |
| 문서 편집·서버 저장 | 구현·운영 서버 확인 | 어떤 플레이리스트에서 사용되는 문서인지 연결 |
| Mac 문서 송수신·백업 | 구현·Intel Mac 자동 검사 완료 | 선택한 플레이리스트에 필요한 문서 자동 수집과 적용 |
| Mac 재생목록 비교·적용 | 기존 로컬 두 파일 비교를 통합 | 서버 플레이리스트 조회·다운로드, 문서 적용과 연결 |
| 플레이리스트 단위 완료·복구 | 미구현 | 일부 문서만 받은 상태를 완료로 표시하지 않는 작업 기록 |

근거: `cloudflare/worker.mjs`의 자료 경로는 `/api/documents`뿐이며 `schema.mjs`에도 문서·문서 버전 테이블만 있다. `web-editor/cloud.js`는 문서 라이브러리를 열고 `.pro6`만 업로드한다. `mac-app/PPSPlaylistController.m`은 운영/최신 로컬 파일을 고른다. `YBDocumentsController.m`은 전체 문서 목록에서 수동으로 선택하고, `YBLibrary.m`은 그 문서별로 송수신한다. 세 탭을 한 창에 넣은 것이 서버 플레이리스트 동기화 완료를 뜻하지 않는다.

## 제공 원본에서 확인한 구조

실제 파일은 로컬에서만 분석했으며 소스 저장소/자동 검사에 올리지 않는다.

- 제공된 주 재생목록 파일 하나에 상위 플레이리스트 19개, 문서 항목 178개, 구분 항목 1개가 있다. 파일 하나를 플레이리스트 하나로 가정하면 안 된다.
- 문서 경로를 한글 NFC로 정규화하면 고유 참조는 126개다. 이 중 23개는 둘 이상의 플레이리스트에서 공유된다. 반복 사용 항목과 실제 문서 파일의 식별자를 구분해야 한다.
- 문서 항목은 `filePath`, 항목 `UUID`, `selectedArrangementID` 등의 속성을 갖는다. 항목 UUID를 문서 UUID로 취급하지 않는다.
- Mac의 `~/Documents/ProPresenter6/...` 경로와 분해형 한글이 있다. 등록한 문서 루트 기준 상대경로와 정규화로 대응시키되 원본 XML의 경로는 보존한다. 파일명만 같다고 자동 연결하지 않는다.
- 제공된 두 `.pro6` 표본의 문서 UUID가 같다. 문서 UUID 하나만으로 원본/복사본을 구분할 수도 없다.

## 다음 구현 기준

아래는 구현 예정 계약이며, 현재 API가 이 기능을 제공한다는 뜻이 아니다.

1. **최초 등록:** `.pro6pl` 원본을 보존하고 파일 안의 플레이리스트별 ID·이름·순서·문서 참조를 읽는다. 기존 `.pro6` 라이브러리와 문서 ID를 대응시켜 정상/누락/모호함을 표시한다. 최초 자료 수집은 Mac 또는 파일 가져오기로 시작할 수 있다.
2. **웹의 기본 진입:** 플레이리스트 목록에서 예배를 고르면 순서대로 찬양·말씀 항목이 보인다. 항목을 열면 기존 문서 편집기를 재사용하고 저장 후 같은 플레이리스트로 돌아간다. 전체 문서 라이브러리는 보조 탐색 기능이다.
3. **문서 연결:** 순서 항목마다 별도 ID와 참조 문서 ID를 둔다. 공유 문서 수정이 영향을 주는 다른 플레이리스트를 보여준다. 기본은 기존 PP6처럼 같은 문서의 변경을 공유하며, 예배별 별도 버전은 명시적인 복사/연결 교체로 제공한다. 조용히 문서를 복제하지 않는다.
4. **동기화 계획:** Mac에서 플레이리스트 하나를 고르면 그 플레이리스트의 순서와 참조 문서 버전·SHA-256을 고정한 목록을 만든다. `.pro6pl` bytes가 같아도 안의 문서 버전이 바뀌면 받기 대상이다. 적용 직전 서버·로컬 기준 버전을 다시 확인한다. 필수 문서가 누락되거나 대응이 모호하면 완료로 진행하지 않는다.
5. **적용:** 필요한 파일을 먼저 내려받아 검증 → 문서/재생목록 백업 → 문서 적용 → 선택한 재생목록 노드만 적용 → 참조와 순서 검증 → 완료 기록. 다른 플레이리스트 노드와 원본 문서는 자동 삭제하지 않는다. 공유 문서 변경의 영향은 적용 전에 표시한다.
6. **중단·충돌:** 기존 문서 엔진을 재사용하되 플레이리스트 작업을 묶는 기록과 재개/복원을 추가한다. 중간 실패를 전체 성공으로 표시하지 않는다. 로컬과 서버 양쪽의 수정은 자동으로 덮어쓰지 않는다.

## 완료를 판단할 시험

1. 기존 플레이리스트를 서버에 등록하고 웹에서 같은 이름·순서·구분 항목을 확인한다.
2. 그 안의 찬양 한 곡의 가사만 수정한다. 재생목록 구조가 같아도 Mac의 해당 플레이리스트에 문서 변경이 표시되어야 한다.
3. 문서를 따로 찾아 고르지 않고 플레이리스트를 동기화하면 수정한 문서가 올바른 PP6 경로에 적용되어야 한다.
4. 곡 추가·교체·순서 변경을 저장하고 Mac의 선택한 플레이리스트에만 반영되는지 확인한다. 항목 추가/삭제와 라이브러리 문서 삭제를 구분한다.
5. 여러 플레이리스트에서 공유하는 찬양의 영향, 동일 파일명/중복 UUID, 누락 문서, Mac 한글 경로를 검사한다.
6. 비교 후 서버 변경·로컬 수정, 전송 실패·적용 중단을 검사하고 미완료 표시·복구·다른 플레이리스트 보존을 확인한다.
7. 교회 High Sierra에서 새 앱으로 동기화한 뒤 PP6의 같은 플레이리스트를 열어 문서 내용·순서·배경 연결을 확인한다.

기존 문서 업로드/편집/수신 검사는 2~3을 만들기 위한 하위 검사다. 그 검사 성공만으로 위 작업 흐름이 완료됐다고 안내하지 않는다. 서버 목록·문서 연결·웹 진입·Mac 작업 계획과 자동 검사는 집 Windows에서 계속 개발할 수 있다. High Sierra 실행과 실제 PP6 결과 확인만 교회 실기 항목이다.
