# 예배온 Sync 설계 (규약 2판)

Mac Sync 2와 서버 사이의 약속이다. 1차(받기)와 2차(올리기·보관본·상주 모드·장치 열쇠)는 구현·배포됐고, 이미지(5.4)와 검색 색인 파일(7.6), Studio 상태 표시(7.2)는 다음 차수다. 구현 상태는 [STATUS](../STATUS.md)·[BACKLOG](../BACKLOG.md)가 기준이고, 이 문서는 규칙만 적는다. 결함 분석(F01–F08, A1–A16)과 작성 경위는 claude.ai 프로젝트 「예배온」 문서에 있다.

## 0.5 이 프로젝트의 기본 모델 (저장소 문서·운영 사이트에서 확인)

재설계가 전제로 삼는 사실이다. 사용자 의도와 다르면 여기부터 고친다.

**목적.** PP6는 교회 구형 Mac에만 있다. 집에서 브라우저(Studio)로 예배 자료를 편집하고, 교회 Mac은 예배 전에 Sync로 받아 PP6가 열게 한다. 사용자는 매번 다운로드·덮어쓰기를 하지 않으려고 Sync를 둔다. Sync는 최소 기능이어야 한다.

**작업 단위는 하위 재생목록(예배) 하나다.** 운영 사이트의 `기본 .pro6pl` v10에는 활성 예배 8개가 있다: 1부 예배(품성), 1부 예배(클래식), 2부 예배, 청년예배, 수요예배, 금요예배, 특별새벽기도, 결혼예배. 보관 7개는 보관함에 있다. 예배 하나의 순서는 대개 `첫화면 → 사도신경 → 찬양 → 기도 → 찬양 → 광고 → 말씀 → 말씀 ppt → 찬양 → 엔딩`이다.

**문서는 두 종류로 쓰인다.**
- **이름만 넣는 문서(찬양):** 그 주에 부를 곡을 검색해 순서에 넣는다. 가사는 대개 고치지 않는다. 가사찬양 1,604·악보찬양 829개.
- **내용을 고치는 문서(말씀·기도·광고):** 매주 같은 파일을 웹에서 고쳐 덮어쓴다(예: 주일예배말씀 v2, 1부기도 v2, 2부 기도 v2가 10-03에 저장됨). 주일예배말씀과 광고는 1부·2부 등 여러 예배가 공유한다. 예배순서 200·특별순서 25개. 카테고리 정책에 따라 이력을 남긴다.

**장부(카탈로그)는 설계의 중심이다.** 사용자는 전체 문서 2,884개의 **이름과 경로만 먼저 서버에 등록**해 두었다. 그래서 원본이 아직 올라오지 않은 찬양도 검색해서 순서에 넣을 수 있고(편집은 불가), Mac은 자기 파일을 그대로 열면 된다. 원본 업로드는 그 뒤를 따라간다. 현재 운영 서버: 장부 2,884개, 원본 309개(말씀·기도·광고를 1순위로 올림), 그 밖에 번호 순으로 올리다 멈춤.

**지금 막혀 있는 지점.** 10-03 웹에서 1부·2부·청년예배 순서를 고쳤고, 장부에서 찬양 4곡을 넣었다. 서버 plan은 원본 없는 참조를 `missing`으로 보고 `ready=false`로 만들며, Sync 0.6.6은 그 예배 전체를 받지 못한다(F03). Studio도 "연결되지 않은 항목이 있습니다. 해당 문서를 Sync에서 올리거나 순서의 연결을 교체하세요"라고 안내한다. **이것은 장부의 설계 의도와 정반대다.** 장부 이름으로 넣은 곡은 Mac에 파일이 있으므로 그대로 받아 열 수 있어야 한다.

**이미 결정된 것(바꾸지 않는다).** 서버가 정본, Mac은 사본. 이력은 지우지 않고 "이전 내용"에서만 보여 준다. 가사·악보찬양은 검색 켬/이력 끔, 예배순서·특별순서는 둘 다 켬, 옛날자료는 둘 다 끔. 이미지는 전체 문서가 참조하는 것이 대상이고 영상은 올리지 않는다. D1은 무료 한도 안에서, 폴링·예약 작업 없이 운영한다. High Sierra 10.13·기본 AppKit만 쓴다. 충돌을 자동 병합하지 않는다. 원본 파일명·경로는 바꾸지 않는다.

**이번 재설계가 바꾸는 것.** "서버 바이트 ↔ Mac 바이트 비교"를 "서버 번호 + Mac 영수증"으로, "파일 전체 기준"을 "노드 기준"으로, "전체 장부 교환"을 "변경 일지 + 이름 변동분"으로, "원본 없으면 예배 전체 차단"을 "원본 없어도 적용"으로, "4개 묶음 업로드 + 매건 전체 상태 저장"을 "연속 큐 + 영수증"으로 바꾼다.

## 0. 요약

- **정본은 서버 하나다.** Mac은 서버 내용을 받아 PP6로 재생하는 기계다. "어느 쪽이 최신인가"는 내용 비교로 정하지 않고 **서버가 매긴 버전 번호**로 정한다.
- 서버는 저장할 때마다 **변경 일지**에 차례번호를 붙여 한 줄씩 남긴다. Mac은 "어디까지 받았나"만 기억하고, 다음에는 그 뒤의 줄만 묻는다. 요청은 한 번이다.
- Mac은 **영수증**을 남긴다. 파일마다 "서버 몇 버전을 받아 어떤 바이트로 썼는지"를 적는다. Mac 쪽 변경은 영수증과 지금 파일을 **같은 Mac 안에서** 비교해 찾는다. 서버와 Mac의 경로 표기·한글 정규화·XML 직렬화 차이에서 오던 오탐은 원리상 생기지 않는다.
- 평소 점검은 **파일 정보(크기·수정시각)만** 본다. 내용을 읽는 것은 수정시각이 바뀐 파일뿐이다. 앱을 켤 때 2,900개를 전부 읽지 않는다.
- 양쪽이 같은 것을 고쳤으면 **서버 것을 적용하고, Mac 것은 서버에 "교회 Mac 수정본"으로 보관**한다. 예배 직전 교회 Mac에서 충돌 창을 띄우지 않는다. 비교와 합치기는 집에서 웹으로 한다.
- 역할은 이렇게 나뉜다.
  - Mac은 "내 파일이 바뀌었나"만 자기 영수증으로 판단하고, 바뀐 것만 올린다.
  - "서버가 바뀌었나"는 서버 번호로 판단한다.
  - 사람이 고르는 일은 웹에서만 한다.
- 예배 전 흐름(수·금·주일 같음)은 이렇다.
  1. Mac이 켜져 있으면 Sync가 상주하면서 바뀐 것을 미리 받아 둔다. PP6가 켜져 있어도 된다.
  2. PP6가 꺼져 있으면 바로 적용한다(설정으로 버튼 한 번 방식도 선택 가능). 수 초면 끝난다.
  3. 예배가 끝나고 PP6를 닫으면 Mac에서 고친 것을 자동으로 올린다.

## 1. 지금 왜 느리고 왜 자꾸 틀리는가

### 1.1 KB 파일인데 시작 점검이 오래 걸리는 이유

파일 크기가 아니라 **개수 × 개수** 구조 때문이다. 아래는 코드에서 확인한 것이고, 실측은 아니다.

| 원인 | 규모 (문서 2,900개가 한 폴더에 있을 때) | 위치 |
|---|---|---|
| 파일 하나를 찾을 때마다 폴더 전체(2,900개) 이름을 읽고 한글 정규화·대소문자 비교를 함 | 파일당 3~4번, 합계 약 3,400만 번의 문자열 생성·정규화 | YBSync.m 84–120, 289–303 |
| 앱을 켤 때마다 2,900개를 전부 다시 읽고 SHA-256을 계산함 | 캐시가 메모리에만 있어 앱을 끄면 사라짐 | YBSync.m 232, 288–296 |
| 사용일 값 하나를 꺼내려고 문서마다 XML 전체를 파싱함 | NSXMLDocument 2,900회 | YBSync.m 294–295 |
| 서버 왕복 약 80회를 순서대로 하고, 요청마다 HTTPS 연결을 새로 맺음 | 문서 목록 29쪽, inventory, 상태보고 약 8, 재생목록 19개 × (plan·보고) | YBServer.m 58–62 외 |
| 서버가 재생목록 plan을 줄 때마다 .pro6pl 전체를 R2에서 읽고 다시 파싱함 | 19회 | playlists.mjs 103–126 |
| 실행할 때마다 inventory 전체와 문서별 상태를 기록함 | D1 쓰기 약 1만 1천 행 | inventory.mjs, sync-observations.mjs |

구형 Mac에서는 첫 줄만으로도 몇 분이 걸릴 수 있는 규모다(추정).

### 1.2 오탐과 "서버 버전을 못 받는" 문제의 뿌리

1. **서버 바이트와 Mac 바이트를 직접 비교한다.** 내용은 같은데 바이트가 다른 상황이 계속 생긴다.
   - Mac은 서버 XML의 경로를 자기 절대경로로 고쳐 쓴 뒤 해시를 비교한다(F01).
   - PP6는 다시 저장할 때 사용일·슬라이드 UUID·미디어 경로를 바꾼다(F02).
   - Studio는 문서를 저장할 때마다 XMLSerializer로 새로 만든다.
2. **기준이 여러 단위로 섞여 있다.** 문서별, 노드별, 파일 전체 기준이 따로 움직이고 서로 앞질러 간다(A1).
3. **자동 판정과 사용자 선택이 같은 문을 쓴다.** 사용자가 서버 쪽을 골라도 아래 단계에서 자동 판정을 다시 한다(F04).
4. **한 항목의 문제가 전체를 멈춘다.** 문서 하나, 이미지 참조 하나, 파일 이름 하나 때문에 탭 전체나 앱 전체가 잠긴다(F03, F05, A2–A4, A8).
5. **장부를 통째로 주고받는다.** 예전에 나온 "장부 대조"가 병목이었던 것은 매번 2,900줄을 오가게 했기 때문이다. 바뀐 줄만 오가면 병목이 없다(4.1).

## 2. 설계 원칙

1. **서버가 정본, Mac은 재생기.** 최신 여부는 서버 버전 번호로만 정한다.
2. **비교는 같은 기계 안에서만 한다.** 서버는 자기 기록끼리, Mac은 자기 영수증과 자기 파일끼리 비교한다.
3. **바뀐 것만 오간다.** 서버에는 변경 일지, Mac에는 영수증을 둔다. 전체 목록 교환과 전체 상태보고는 없앤다.
4. **판정은 보수적으로, 결과는 지우지 않게.** 덮어쓰기 전에 Mac 바이트가 영수증과 다르면 무조건 서버에 보관본을 남긴다. 아무것도 조용히 사라지지 않는다.
5. **실패는 항목별로 처리한다.** 그 항목만 "보류"로 남기고 나머지는 계속한다. 보류 항목은 다음 실행에서 다시 시도한다.
6. **교회 Mac에서는 고르지 않는다.** 예배 직전에는 할 일이 없거나 버튼 하나다. 비교와 합치기는 집에서 웹으로 한다.
7. **동기화 요청은 가볍게 한다.** 무료 요금제 한도(호출당 쿼리 50개, CPU 10ms, 하루 쓰기 10만 행) 안에 들도록, 요청 하나당 D1 문장 수를 상수로 묶는다. 서버는 받는 경로에서 XML을 파싱하지 않고, 스키마 초기화를 요청 경로에서 뺀다.

| | 하는 일 | 하지 않는 일 |
|---|---|---|
| 서버 | 문서·재생목록 노드·이미지의 현재본과 이력, 버전 발급(CAS), 변경 일지, 장치별 "어디까지 받았나·보류 목록" | Mac 파일 목록 보관, 문서별 Mac 상태 보관 |
| Studio | 편집·저장(문서 단위·노드 단위), "교회 Mac 수정본" 비교·채택, 교회 Mac 적용 상태 표시 | Mac 경로 고쳐 쓰기 |
| Sync | 바뀐 것 미리 받기, PP6가 꺼져 있을 때 교체, Mac에서 고친 것 올리기, 영수증 기록 | 전체 목록 대조, 충돌 해결 화면, 서버 문서 삭제, 재생목록 파일 자동 등록 |

## 4. 핵심 장치 세 가지

### 4.1 서버 변경 일지

모든 저장이 같은 batch 안에서 일지에 한 줄을 더한다.

```
sync_log(seq INTEGER PRIMARY KEY AUTOINCREMENT,
         kind      -- 'doc' | 'node' | 'node-state' | 'media' | 'decision'
         entity    -- 문서 id / 'library:node' / 이미지 경로 키
         version, sha256, size, path, author, at)
INDEX (kind, entity, seq)
```

- 일지 INSERT에도 기존 batch와 같은 `write_id` 가드를 건다. CAS가 실패한 저장은 일지에 남지 않는다.
- Mac은 `GET /api/sync/changes?since=<커서>&limit=500` 한 번으로 그 뒤의 변경만 받는다. 같은 개체가 여러 줄이면 마지막 줄만 쓴다. D1 읽기는 돌려받은 줄 수만큼이다.
- 받는 도중 Studio가 다시 저장하면, 이력 끔 문서는 예전 버전 원본이 지워져 404가 날 수 있다. 이때는 문서 head를 다시 읽고 현재본을 받는다.
- 일지는 저장 1회에 1줄이라 작다. 정리가 필요해지면 모든 장치의 커서보다 오래되고 더 새 줄이 있는 줄만 지운다. 장치의 커서가 정리 범위보다 뒤면 서버는 `resync_required`를 돌려주고, Mac은 전체 검사(9.1)를 한다.
- 장부 대조와 다른 점: 장부 대조는 양쪽 장부 전체를 펼쳐 한 줄씩 맞대는 방식이다. 변경 일지는 지난번 이후 새로 적힌 줄만 읽는다. Mac의 장부(영수증)는 Mac 밖으로 나가지 않는다.

### 4.2 Mac 영수증

프로필 폴더에 SQLite 파일 하나(`receipt.sqlite`)를 둔다. macOS에 기본으로 들어 있고 10.13에서 쓸 수 있다. 지금처럼 파일 하나 처리할 때마다 JSON 전체를 fsync로 다시 쓰는 방식(F07-C)을 대신한다.

| 표 | 내용 |
|---|---|
| docs | 서버 id, 경로 키(NFC), 디스크의 실제 이름, 받은 서버 버전, 쓴 바이트 sha, 쓴 내용의 의미 지문, 크기, 수정시각(ns), inode |
| nodes | 재생목록 id, 노드 id, 받은 노드 버전, 쓴 노드의 의미 지문, 노드 이름 |
| media | 경로 키, sha, 크기, 수정시각 |
| pending | 커서는 지나갔지만 아직 끝나지 않은 항목(개체, 목표 버전, 이유). 다음 실행에서 다시 시도한다 |
| outbox | 올려야 할 Mac 수정분과 진행 단계. 재시작 후 이어서 한다 |
| meta | 받은 마지막 seq, 마지막 적용 회차 |

장치 정보는 영수증과 따로 둔다. 장치 id와 서버가 발급한 장치 토큰은 설정 폴더와 키체인에 보관하고, 서버에 등록된 장치만 Studio에 표시한다. 영수증을 다시 만들어도 장치가 바뀌지 않는다(A14).

### 4.3 의미 지문

Mac 파일이 실제로 고쳐졌는지 판단하는 값이다. 영수증에 적힌 지문도 **같은 Mac이 같은 함수로** 계산한 것이라서, 서버와 계산 방식을 맞출 필요가 없다.

**차단목록 방식**으로 만든다. 문서 전체를 정규화하되, 알려진 휘발성 값만 뺀다. 남겨야 할 것만 고르는 방식(허용목록)은 PP6에서 실제로 고친 것을 놓친다.

- 공통 정규화: 속성 순서·따옴표·공백을 무시하고, 숫자 표기를 통일한다.
- 문서(.pro6)에서 빼거나 바꾸는 것
  - 루트의 `lastDateUsed`, `usedCount`, 빌드·버전 번호
  - 슬라이드·요소·arrangement의 UUID는 등장 순번으로 바꾼다. arrangement가 슬라이드를 가리키는 관계는 그대로 남는다.
  - 글은 RTF 원문 대신 **글자 + 핵심 서식**(글꼴, 크기, 색, 굵게·기울임)으로 비교한다. PP6가 RTF를 다시 인코딩해도 흔들리지 않게 하기 위해서다.
  - 이미지는 경로 대신 **파일 내용 sha**로 본다. 영상은 경로 키 + 크기로 본다.
- 재생목록 노드에서 빼는 것: `modifiedDate`, cue UUID.
  - 항목은 (종류, 가리키는 문서의 경로 키, 표시 이름, arrangement)로 본다.
  - 경로 키를 만드는 순서: file URL을 한 번 디코딩한다 → `~`와 `/Users/<이름>/`을 정리한다 → 문서 폴더 기준 상대경로로 바꾼다 → NFC로 맞춘다.
- 지문은 **수정시각이 바뀐 파일에만** 계산한다. 보통 한 주에 수십 개다.
- 안전망: 지문이 같아도 바이트가 영수증과 다른 파일을 서버 것으로 덮게 되면, 덮기 전에 Mac 바이트를 서버에 "기술적 차이" 보관본으로 남긴다. 웹 화면에서는 기본으로 숨긴다. 지문이 놓친 수정이 있어도 사라지지 않는다.
- 바탕은 `PP6Core.m`의 기존 지문이다. 다만 지금 그 지문은 slide label·notes·hotKey와 서식을 빠뜨리고 Text·Image·Video 요소만 보므로, 위 기준으로 고친다.

## 5. 판정 규칙

### 5.1 한 항목의 상태는 네 가지

| 서버 | Mac | 상태 | 동작 |
|---|---|---|---|
| 그대로 | 그대로 | 같음 | 없음 |
| 바뀜 | 그대로 | **받기** | 서버 것을 준비해 두었다가 적용 |
| 그대로 | 바뀜 | **올리기** | Mac 것을 서버 새 버전으로 저장. 작성자는 장치 이름 "교회 Mac" |
| 바뀜 | 바뀜 | **서버 적용 + Mac 보관본** | Mac 것을 서버에 "교회 Mac 수정본(미적용)"으로 보관한 뒤 서버 것을 적용 |

**서버 바뀜**은 서버 버전이 영수증의 버전보다 큰 것이다. 내용은 비교하지 않는다.

**Mac 바뀜**은 아래 순서로 판단한다.
1. 크기·수정시각·inode가 영수증과 같으면 그대로다.
2. 다르면 바이트 sha를 계산한다. 영수증과 같으면 그대로다.
3. 다르면 의미 지문을 계산한다. 같으면 "사용 기록만 바뀜"이다. 그대로로 취급하고, 영수증의 파일 정보와 sha를 새 값으로 바꾸고, 사용일만 서버에 알린다(7.3).
4. 지문도 다르면 바뀜이다.

**적용 직전 재확인:** 준비와 적용 사이에 PP6에서 고친 파일을 덮지 않게 한다. 적용 직전에 항목마다 준비 때 기록한 파일 정보와 비교하고, 달라졌으면 그 항목만 다시 판정한다. 결과가 올리기나 보관본이면 그것을 먼저 하고 적용하며, 할 수 없으면 그 항목을 보류한다.

**웹에서 한 결정이 자동 판정보다 우선한다.** 예를 들어 웹에서 "이번엔 Mac 것 유지"를 고르면, 그 결정이 일지(`decision`)로 Mac에 전달된다. 아래 단계가 그 결정을 다시 뒤집지 않는다(F04 재발 방지).

### 5.2 문서와 장부

**설계 목표는 원본 전체 업로드다.** 장부(이름·경로만 있는 줄)는 초기 구축 중에 원본보다 먼저 올라가는 다리이고, 구축이 끝난 뒤에는 "Mac에 어떤 파일이 있나"를 아는 이름 색인으로 남는다. 둘은 역할이 다르므로 표를 따로 두어도 된다. 다만 **정체성은 하나**여야 한다.

| | 장부 줄(`library_catalog`) | 문서 줄(`documents`) |
|---|---|---|
| 생기는 때 | Mac이 이름·크기만 보낼 때. 파일을 읽지 않아 2,900개도 수 초 | 원본이 올라올 때 |
| 아는 것 | 경로, 크기, Mac 보유 여부 | 버전, sha, 본문 색인, 카테고리, 사용일, 슬라이드 수 |
| Studio | 검색·순서 넣기 가능, 편집 불가, "원본 요청" | 편집 가능 |
| Mac | 자기 파일을 그대로 쓴다 | 영수증과 비교해 받기·올리기 |

- 지금은 두 표가 서로 다른 id를 쓰고 경로로만 이어진다. 원본이 올라올 때 **장부 줄의 id를 문서 줄이 이어받게** 한다. 그러면 웹 순서나 보관본이 장부 id로 가리킨 문서가 업로드 뒤에도 같은 것으로 이어진다.
- 장부 줄은 Mac이 처음 연결할 때 만들고, 그 뒤로는 **이름 변동분만** 보낸다(새 파일, 이름 바뀜, 없어짐). 장치별 전체 목록을 매번 다시 쓰는 inventory는 없앤다.
- 재생목록 노드는 지금처럼 `~/Documents/ProPresenter6/<경로>` 형식으로 문서를 가리킨다. 사용자가 확인한 실제 Mac 경로다. 서버 안에서는 장부 id로 대응한다.
- Studio의 "서버 저장"은 지금도 원본 없는 곡이 있어도 막히지 않는다. 막히는 곳은 Mac이 받는 단계(plan `ready=false`)뿐이다. 이것만 푼다.

| 상황 | 처리 |
|---|---|
| 서버에만 있음(웹에서 새로 만든 문서) | 받기. 놓을 자리에 같은 이름의 파일이 이미 있으면(NFC, 대소문자 무시로 확인) 덮지 않고 "확인 필요"로 보류한다(A9) |
| Mac에만 있음(PP6에서 새로 만든 문서) | 장부에 이름을 올리고, 우선순위에 따라 원본을 올린다 |
| Mac에서 이름이 바뀜 | 같은 inode가 새 이름에 있으면 장부 줄의 이름을 바꾼다. 옛 이름으로 다시 받지 않는다. 그 문서를 쓰는 서버 노드의 경로도 함께 바꾸고 일지에 남긴다 |
| Mac에서 지워짐 | 서버 원본은 지우지 않는다. 장부에 "Mac에 없음"으로 표시하고, 활성 재생목록이 그 문서를 쓸 때만 다시 받는다 |
| 이름 규칙 위반, 빈 파일, 깨진 XML | 그 파일만 "제외"로 표시하고 계속한다(A8). 장부에는 올린다 |

### 5.3 재생목록 노드 (금요기도회 1부 같은 하위 재생목록)

- **단위는 노드다.** 파일 전체 기준과 파일 전체 PUT은 없앤다(A1의 근본 해결).
- **받기**
  - 서버 노드 XML을 Mac `.pro6pl` 안의 같은 노드 자리에 그대로 끼운다. 다른 노드의 바이트는 건드리지 않는다.
  - 새 노드는 서버 순서의 자리에 넣는다. 최상위 노드 사이의 순서는 Mac 것을 유지한다.
- **경로**
  - 노드 안의 문서 경로(`filePath`)는 고쳐 쓰지 않고 서버 것을 그대로 쓴다.
  - 판정은 4.3의 경로 키로 하므로 `~`·절대경로, NFC·NFD 차이가 상태에 영향을 주지 않는다(F01 근본 해결).
  - PP6가 `~/Documents/…` 형식을 여는지는 실기 확인이 필요하다(11장 1번). 열지 못하면 Mac이 쓰는 순간에만 절대경로로 바꾸고, 판정은 그대로 경로 키로 한다.
- **문서가 없는 노드도 적용한다.** 노드가 가리키는 문서가 서버에 없어도 노드를 적용한다. 그 문서가 Mac에 있으면 그대로 쓰고, 양쪽에 다 없으면 "문서 없음 n개"로 표시한다(F03 근본 해결).
- **웹에서 보관·삭제한 노드**는 Mac 파일에서 뺀다. 빼기 전의 노드 XML은 적용 회차 백업에 남고, 문서 파일은 지우지 않는다.
- **올리기**에는 "노드 XML 교체" 요청을 새로 둔다.
  - Mac은 노드 XML 하나만 보낸다(파일 전체가 아님). 서버는 그 노드만 검증한다.
  - CAS는 Studio가 이미 쓰는 노드 sha(`baseNodeHash`)와 노드 버전으로 한다.
  - 보관·삭제된 노드에 온 Mac 수정은 노드 보관본으로 받는다. 되살아나지 않는다.
- **PP6에서 노드를 만들거나 지웠을 때**
  - PP6에서 만든 노드는 서버에 새 노드로 등록한다.
  - PP6에서 지운 노드는 서버에서 지우지 않는다. "Mac에서 지움"으로 표시하고 웹에서 확정한다. 확정하기 전까지 서버가 그 노드를 고쳐도 Mac에 다시 넣지 않는다.
- **UUID 없는 노드**는 지금 이름이 id다. 이름을 바꾸면 지문이 같은 노드끼리 짝지어 "이름 바뀜"으로 처리한다.

### 5.4 이미지

**교회 Mac의 실태 (2026-10-04, 정리본 2,884개 선행 검사)**

- 참조는 `RVImageElement`·`RVVideoElement`의 `source` 속성이다. 표기가 두 가지로 섞여 있다.
  - URL형: `file:///Users/Shared/Renewed%20Vision%20Media/ImportedImages/<PPT폴더>/Slide1.jpg`
  - 원시형: `/Users/Shared/Renewed Vision Media/Images/찬양-PPT_4.jpg`
  - 한글이 NFD로 적힌 것이 있다(HFS+ 시절 파일).
- 미디어 루트 `/Users/Shared/Renewed Vision Media/` 아래에 영상·오디오·이미지 폴더가 여럿 있다. 서버에 두는 것은 이미지뿐이고, 대상 폴더는 **`Images`와 `ImportedImages` 두 개**다.
  - `ImportedImages`는 PPT 파일명(변환되어 알아보기 어려움)으로 된 하위 폴더마다 `Slide1.jpg, Slide2.jpg, …`가 들어 있다. **같은 이름의 파일이 수백 개이므로 이름으로 합치면 안 되고, 전체 경로로만 구분한다.**
  - `PasteBoardImages`도 참조된다(문서 2개, 28회, 파일 24개). 옛 자료라 서버에 둘 가치가 없어 **기본 제외**한다.
- 미디어 루트 밖을 가리키는 참조는 0건. 다만 `ImportedImages` 안에서 원본을 찾지 못한 요소 268개와 빈 경로 29개가 있다. 이것은 Mac에서도 이미 깨진 참조이므로, 업로드 대상이 아니라 "원본 없음" 목록으로만 남긴다.

**규칙**

- **경로 키는 Mac 절대경로다.** 두 표기를 하나로 맞춘다: file URL이면 host·query 없이 한 번만 percent 디코딩하고, 그 결과를 **NFC**로 정규화한다. Mac에서 파일을 찾을 때는 NFC·NFD 두 이름을 모두 시도한다. 문서 바이트는 고치지 않는다(원본 파일명·경로 불변 원칙).
- **이미지 때문에 문서를 막지 않는다.** 이미지가 없어도 문서는 적용하고, 그 예배를 "적용됨 · 이미지 n개 없음"으로 표시한다. 이전 결정대로 이 상태는 "완료"가 아니다.
- **문서 버전마다 참조를 따로 두지 않는다.** 대신 라이브러리 공용 **이미지 경로표**(`media_paths: 경로 키 → sha256, 크기`)를 둔다. 문서를 어디서 저장하든 경로표는 그대로 유효하다(A2의 원인 제거). 한 sha에 여러 경로가 매달릴 수 있고(동명 Slide 파일·복제본), 바이트는 R2에 sha당 한 번만 둔다.
- **허용 폴더 세 개.** 서버와 교신하는 이미지 폴더는 `/Users/Shared/Renewed Vision Media/` 아래 세 개로 고정한다.
  | 폴더 | 내용 | 방향 |
  |---|---|---|
  | `Images/` | PP6에서 직접 넣은 이미지 | Mac → 서버(등록·올리기), 서버 → Mac(없을 때만) |
  | `ImportedImages/<PPT폴더>/` | PP6의 PPT 가져오기 산출물 | 같음 |
  | `YebaeOn/` | **웹(Studio)에서 가져온 이미지 전용**. 새로 만드는 폴더 | 서버 → Mac이 기본. Mac에서 손대지 않음 |
  경로표에 그 밖의 경로가 있어도 받지 않고 "허용 폴더 밖"으로 알린다. 서버도 등록 시 같은 접두로 제한한다. `YebaeOn/` 폴더가 없으면 Sync 2가 첫 적용 때 만든다. 이름은 ASCII로 두어 NFC/NFD 문제를 피한다.
- **Mac이 문서를 적용할 때**, 그 문서 안의 이미지 경로마다 이렇게 한다.
  1. 경로표에 없으면 건드리지 않는다(Mac에만 있는 이미지, 혹은 이미 깨진 참조).
  2. 경로표에 있고 Mac에 파일이 없으면, 허용 폴더 안일 때만 서버에서 sha로 받아 그 경로에 둔다. 받은 바이트의 sha를 확인하고 임시 이름으로 쓴 뒤 바꾼다.
  3. 경로표에 있고 Mac에 파일이 있으면 **sha256을 비교한다.** 같으면 그대로 둔다. 다르면 **덮지 않고 사본도 만들지 않으며** "확인 필요 · 내용이 다른 이미지"로 보고한다. 사본 자동 생성은 오탐 때 사본이 늘어나는 것이 더 큰 손해이므로 하지 않는다. 실제로 다른 이미지가 필요하면 웹에서 새 경로로 넣는 것이 올바른 길이다.
  - sha 비교 비용: 영수증에 경로별 (크기, mtime, sha)를 적어 두고 stat이 같으면 다시 해시하지 않는다(문서와 같은 방식). 처음 한 번만 전체를 읽는다.
- **웹에서 가져온 이미지(PPT 등)**
  - 지금의 가짜 경로 `file:///YebaeOn-Media/<sha>.png` 대신 **`/Users/Shared/Renewed Vision Media/YebaeOn/<이름>`** 의 실제 경로로 저장한다. 전용 폴더라 PP6가 직접 넣은 이미지(`Images/`)와 섞이지 않고, "이 폴더 안은 서버가 주인"이라는 규칙이 단순해진다. 11절 결정 5는 이것으로 닫는다.
  - 이름은 사람이 알아볼 수 있게 `<문서이름>-<n>.<ext>`로 하고, 같은 이름이 경로표에 이미 있으면 번호를 올린다. 하위 폴더는 만들지 않는다.
  - `YebaeOn/` 안에서는 5.4 적용 규칙 3의 "내용이 다르면 확인 필요"가 거의 생기지 않는다. 서버가 쓴 파일뿐이기 때문이다. 생긴다면 누군가 Mac에서 손댄 것이므로 역시 덮지 않고 보고만 한다.
  - 그러면 Mac이 문서 바이트를 고쳐 쓸 일이 없다. 이미 가짜 경로로 저장된 문서 몇 개는 이관 때 한 번 바꾼다.
- **Mac에서 서버로**
  - 결정된 범위대로 **전체 문서가 참조하는 이미지**를 올리고, 영상은 올리지 않는다.
  - 처음 한 번은 전체를 등록하고(9.2, 집 PC에서 `bulk-media.mjs`), 그 뒤로는 올리는 문서에서 새로 생긴 이미지만 올린다.
- **정리:** 이미지 정리는 지금처럼 수동 후보 검토로만 한다. 후보를 계산할 때는 현재본·보관본·이력 문서를 파싱해 쓰임을 확인한다. 유한한 작업이다.

### 5.5 문서 성격별 흐름

원본 전체 업로드가 끝나면 모든 문서는 같은 규칙(5.1)으로 돈다. 아래 구분은 **초기 구축 중**에 무엇부터 올리고, 원본이 없는 동안 무엇이 되어야 하는지를 정하는 것이다.

| 성격 | 예 | 서버에 필요한 것 | 흐름 |
|---|---|---|---|
| **참조 문서** | 그 주에 부를 찬양 | 이름·경로 장부만 있으면 된다 | 웹에서 장부 이름으로 순서에 넣는다. Mac은 자기 파일을 그대로 쓴다. 원본 업로드는 뒤에서 천천히 한다 |
| **내용 편집 문서** | 말씀, 기도, 광고 | 원본이 반드시 서버에 있어야 한다 | 웹에서 내용을 고치고 Mac이 받는다. 서버가 정본이고, 업로드 1순위다 |
| **웹에서 새로 만든 문서** | 새 말씀 문서, 주보 적용 문서 | 서버에서 만들어진다 | Mac 문서 폴더에 새 파일로 받는다 |

**업로드 순서** (약 2,650개를 한 번에 올리지 않고 쓰임 순서대로)
1. 활성 재생목록이 쓰는 내용 편집 문서(예배순서·특별순서 카테고리)
2. 활성 재생목록이 쓰는 나머지 문서
3. 그 밖의 전체 문서. 상주 모드에서 뒤에서 이어 간다.

**원본 요청:** 장부 이름만 있는 문서를 웹에서 고치고 싶을 때 쓴다.
- Studio에서 "원본 요청"을 누르면 서버가 요청을 일지(`decision`)에 남긴다.
- Mac이 다음 확인 때(상주 중이면 15분 이내) 그 문서를 먼저 올린다.
- 그 뒤로는 내용 편집 문서와 같은 흐름이다.

**공유 문서:** 같은 말씀·광고 문서를 여러 순서가 함께 쓰면, 웹에서 한 번 고친 것이 그 문서를 쓰는 모든 순서에 반영된다. 운영 사이트에서 주일예배말씀·광고·첫화면·사도신경은 1부(품성)·1부(클래식)·2부·청년예배가 함께 쓴다. 이것은 PP6와 같은 동작이다. Studio는 저장할 때 "n곳에서 함께 씀"을 보여 준다.

**운영 방식(사이트에서 확인):** 말씀·기도·광고는 매주 같은 파일을 덮어쓴다. 수요예배·금요예배는 각자의 말씀 문서(수요예배.pro6, 금요예배말씀.pro6)를 쓴다. 이력은 예배순서 카테고리 정책대로 남고, "이전 내용"에서만 보인다.

**Studio 쪽에서 고칠 것(이 설계의 일부):**
- 순서에 원본 없는 문서가 있어도 저장과 Mac 적용이 막히지 않는다. 안내 문구는 "원본 없음 n개 · Mac에서는 그대로 열림 · 편집하려면 원본 요청"으로 바꾼다.
- 순서 항목의 상태 표시를 셋으로 나눈다: 편집 가능(원본 있음) / 원본 없음 / Mac에 없음(장부에도 없는 이름).
- 재생목록 저장은 노드 단위다. 파일 전체 버전 표시("v10")는 노드 버전과 저장자·시각으로 바꾼다.

## 6. 동기화 한 번의 흐름

### 6.1 단계

```
① 준비 (PP6가 켜져 있어도 됨, 보통 수 초)
   변경 일지 받기(요청 1번) + 보류 목록
   → 문서 폴더 스캔(readdir 1번 + 파일 정보) → 판정
   → Mac 수정분과 보관본을 먼저 올림
   → 받을 파일을 임시 폴더에 내려받고 sha 확인
② 적용 (PP6가 꺼져 있어야 함, 보통 1~2초)
   항목마다 재확인(5.1) → 회차 기록 저장
   → 이미지 → 문서 → 재생목록 파일 순서로
     "현재 파일을 백업 폴더로 이름 바꾸기 → 준비한 파일을 제자리로 이름 바꾸기"
③ 기록
   영수증을 트랜잭션 한 번으로 갱신(커서, 보류 목록 포함)
   → 서버에 한 줄 보고(장치, 받은 seq, 시각, 개수, 보류 목록)
```

- **올리기를 받기보다 먼저 한다.** 받기가 Mac 것을 덮어도 서버에 남아 있게 하기 위해서다. 올린 결과는 일지에 다시 나타나므로, 영수증에 이미 적힌 버전과 sha와 같으면 건너뛴다.
- **내려받기**는 연결 하나를 유지한 채 동시에 4개씩 한다. 버전을 지정해서 받으므로, 도중에 웹에서 다시 저장하면 그 저장은 다음 회차에 들어온다. 지금처럼 "비교 후 서버가 바뀌었습니다"로 중단하지 않는다.
- **적용**은 같은 디스크 안에서 이름만 바꾸므로 파일을 복사하지 않는다. 백업도 이름 바꾸기로 생긴다. 백업은 최근 10회 분량만 남긴다(백업 결론 문서).
- **커서와 보류:** 커서는 앞으로 가지만 끝나지 않은 항목은 보류 목록에 남는다. 보류 목록은 서버에도 보고하므로, Studio가 "적용됨"을 잘못 표시하지 않는다.

### 6.2 언제 도는가 (수요·금요·주일 예배 모두 같은 흐름)

Sync는 요일을 구분하지 않는다. 교회 Mac이 켜져 있는 동안 **상주 모드**로 돌며 서버를 따라간다.

| 계기 | Sync가 하는 일 |
|---|---|
| Mac 로그인(로그인 항목) | 앱만 뜨고 **바로 돌지 않는다.** 구형 Mac은 부팅 뒤 한참 인터넷을 못 잡는다(사용자 확인). 네트워크 도달 알림(SCNetworkReachability)을 기다렸다가, 서버 응답이 한 번 성공한 뒤에 ① 준비. 최대 10분까지 간격을 늘리며 조용히 기다리고, 그동안 실패 창을 띄우지 않는다 |
| 잠자기에서 깨어남 | ① 준비 |
| 상주 중 15분마다(설정 가능) | 변경 일지만 물어봄(요청 1번). 새 줄이 있을 때만 ① 준비 |
| 준비가 끝났고 PP6가 꺼져 있음 | **자동 적용**(11장 결정 3). 끄면 적용 버튼 한 번 |
| PP6가 켜져 있음 | "적용 대기 n개 · PP6를 닫으면 적용"을 표시. PP6가 닫히면 Mac 수정분을 먼저 올리고 적용 |
| PP6 종료(예배 후) | 고친 파일만 판정해 **Mac 수정분 자동 올리기**, 사용일 보고 |
| 사용자가 누름 | ① 준비 → (PP6 꺼져 있으면) 적용 |

**주중 흐름 예:** 월~수 집에서 수요예배를 편집한다. 수요일 저녁 교회 Mac을 켜면 수 초 안에 적용이 끝나 있다. 예배 중 PP6에서 고친 것은 PP6를 닫을 때 서버로 올라간다. 목·금 집에서 금요예배를 편집하면 같은 흐름이 반복된다. Mac을 끄지 않고 두면 15분마다 따라가므로, 예배 직전에는 할 일이 없다.

**상주 확인의 비용**(추정): 15분마다 1번이면 하루 96번 요청이다. 새 변경이 없으면 D1 읽기가 거의 0이고 쓰기는 0이다. 무료 한도(하루 요청 10만, 읽기 500만 행)에 비하면 무시할 수준이다. 서버가 Mac을 깨우는 방식(웹소켓 등)은 유료 기능과 상시 연결이 필요해서 쓰지 않는다.

- 로그인 시 실행은 `~/Library/LaunchAgents`의 plist로 한다. 10.13에서 별도 도우미 앱 없이 된다.
- PP6 실행·종료 감지는 NSWorkspace 알림을 쓰고, 잠자기 깸 감지는 `NSWorkspaceDidWakeNotification`을 쓴다.
- 상주 중에는 창을 닫아도 메뉴 막대에 남는다. 이때 하는 일은 위 표의 계기에서만 일어나며, 계속 디스크를 훑거나 CPU를 쓰지 않는다.

### 6.3 PP6가 옛 내용을 다시 쓰는 경우

PP6는 재생목록을 메모리에 들고 있다가 종료할 때 파일에 다시 쓸 수 있다(11장 확인 4). 적용 전에 열린 PP6가 나중에 닫히면서 옛 순서를 덮어쓰면, 이것을 "Mac 수정"으로 올려 서버 편집본을 되돌리는 위험이 생긴다(A1과 같은 꼴).

- 적용은 PP6가 꺼져 있을 때만 한다. 적용 도중 PP6가 켜지면 적용을 마친 뒤 "PP6를 다시 열어 주세요"를 띄운다. 적용은 1~2초면 끝난다.
- **되돌림 감지:** Mac에서 바뀐 노드·문서의 지문이 마지막 적용에서 **교체되어 백업으로 간 내용**과 같으면, 사람이 고친 것이 아니라 PP6가 옛 내용을 다시 쓴 것으로 본다. 올리지 않고 서버 것을 다시 적용하며, 결과에 "PP6가 옛 내용을 다시 씀 · 다시 적용"으로 남긴다.

## 7. 서버 규약

### 7.1 새로 두거나 바꾸는 것

| API | 내용 | D1 |
|---|---|---|
| `GET /api/sync/changes?since=&limit=` | 변경 일지 조각 + `head`, `next` | 돌려준 줄 수 |
| `GET /api/documents/:id/content?version=` | 기존 API. 404면 head를 다시 읽고 현재본을 받음 | 1행 |
| `GET /api/playlists/:lib/nodes/:node?version=` | 노드 XML 한 개를 노드 이력 표에서 줌 | 1행 |
| `GET /api/media/content?sha=` | 기존 API | 0~1행 |
| `PUT /api/documents/:id` + `If-Match` | 기존 API. 작성자는 장치 이름 | 지금과 같음 |
| `POST /api/sync/revisions` | Mac 수정본(문서·노드)을 **현재본이 아닌 보관본**으로 저장. 별도 표 + R2 `revisions/` 접두. 이력 끔 문서의 정리에 걸리지 않으며, 해결 상태 열이 있음 | 2문장 |
| `PUT /api/playlists/:lib/nodes/:node` | 노드 XML 교체. 노드 하나만 검증하고, 노드 sha·버전으로 CAS | 수 문장 |
| `POST /api/documents` | 기존 API(새 문서) | 지금과 같음 |
| `POST /api/sync/usage` | `[{id, lastDateUsed, usedCount}]`를 `UPDATE … FROM json_each` 한 문장으로 반영. `last_used`는 기존 값과 비교해 큰 쪽(MAX)을 남기고 `usage_version`도 맞춤. 버전은 만들지 않음 | 1문장 |
| `POST /api/sync/devices/:id/applied` | 장치 한 줄과 보류 목록 갱신 | 1~2행 |
| `POST /api/sync/manifest` | 처음 등록용. 50개씩 `json_each` 한 문장으로 없음·같음·다름을 판별 | 1문장 |
| `PUT /api/media/paths` | 이미지 경로표 등록. body `{paths:[{path, sha256, size}]}` 최대 200개, `json_each` 한 문장으로 INSERT OR REPLACE. path는 NFC 절대경로, 허용 접두(`/Users/Shared/Renewed Vision Media/` 아래 `Images/`·`ImportedImages/`·`YebaeOn/`) 밖이면 그 항목만 `rejected`로 돌려줌. sha가 R2에 없으면 `unknown` | 1문장 |
| `GET /api/media/paths?path=…` (여러 개) | 경로 키로 sha·크기 조회. Sync 2가 적용할 문서의 이미지 경로를 50개씩 물음 | 1문장 |
| 장치 등록·토큰 | 장기 토큰을 발급하고 웹에서 폐기할 수 있음. 30일마다 예배 직전에 다시 로그인하지 않아도 됨 | 1행 |

- **문서 PUT도 last_used를 MAX로 저장한다.** 웹에서 저장할 때 XML 안의 옛 사용일로 되돌아가지 않게 한다.
- **스키마 초기화를 요청 경로에서 뺀다.** 지금은 isolate의 첫 요청마다 약 29개 문장이 붙는다. 이것을 배포 때 한 번 실행하는 마이그레이션으로 옮긴다. 쓰지 않게 된 표는 사용자 승인 후 별도 마이그레이션으로만 지운다.
- **Sync 요청에는 `X-YebaeOn-Sync: 2` 머리글을 붙인다.** 전환 후에는 이 머리글이 없는 Mac 쓰기를 서버가 거절해서, 옛 앱이 서버 편집본을 덮지 못하게 한다.
- **기존 Studio 저장도 `sync_log`에 한 줄을 남긴다**(write_id 가드 포함). 대상은 문서 PUT·POST, 노드 PATCH, 보관·복원·삭제, 미디어 가져오기다.

### 7.2 Studio가 보여 주는 Mac 상태

- **"교회 Mac 적용됨 / 대기"**는 Mac이 문서마다 상태를 보고하지 않고 서버가 계산한다. 그 항목의 마지막 seq가 장치의 받은 seq 이하이고 보류 목록에 없으면 "적용됨"이다. 보류 항목은 이유와 함께 먼저 보여 준다.
- **"교회 Mac 수정본 있음"**은 보관본이 있는 항목에 표시한다(기술적 차이 보관본은 숨김). 누르면 현재본과 나란히 비교하고, "이걸로 현재본 만들기"와 "이번엔 Mac 것 유지"를 고를 수 있다.
- 화면 위에 "교회 Mac 마지막 동기화: 10/5 08:41"을 보여 준다.

### 7.3 사용일

- PP6가 송출하면서 바꾼 `lastDateUsed`·`usedCount`는 문서 버전을 만들지 않고 usage로만 올린다. 검색의 최근 사용순은 그대로 유지된다.
- 서버 것을 받아 덮어쓸 때는 Mac 파일의 두 값을 유지한다. 루트 속성만 바꾸며, 이것은 선택 사항이다(11장 결정 4). 이렇게 쓰면 바이트 sha가 서버 sha와 달라지므로 영수증에 둘 다 적는다.

### 7.4 비용 비교 (코드 구조 기준 추산, 실측 아님)

| | 지금 | 재설계 |

| 앱 시작 점검 | 서버 요청 약 80회, D1 쓰기 약 1만 1천 행 | 요청 1회, D1 읽기 수십 행, 쓰기 0 |

### 7.5 업로드 병목과 새 업로드 방식

#### 지금 업로드가 느린 이유 (코드 기준, 소요시간 기여율은 미측정)

| 원인 | 규모 (2,900개) | 위치 |
|---|---|---|
| 4개씩 묶어 보내고, 가장 느린 것이 끝날 때까지 기다린 뒤 다음 묶음으로 감 | 묶음 725번이 줄 세워 진행 | YBLibrary.m 70–103 |
| 묶음마다 상태보고를 보내고 응답을 기다림 | 요청 약 725번 추가 | YBLibrary.m 99 |
| 요청마다 HTTPS 연결을 새로 맺음 | 구형 Mac CPU로 연결 수천 번 | YBServer.m 58–62 |
| 문서 하나 끝날 때마다 state.json 전체를 다시 쓰고 디스크 강제 플러시(fsync, F_FULLFSYNC, 폴더 fsync) | 파일이 문서 수만큼 커지므로 누적 약 420만 항목, 약 1.9GB 쓰기(추산) | YBSync.m 158–175, 355–359 |
| 기록할 때마다 지난 적용 기록 전체를 다시 읽어 검사 | 문서마다 반복 | YBSync.m 273–278 |
| 파일 하나를 찾을 때마다 폴더 2,900개 이름 정규화 | 업로드 경로에서도 문서당 2~3번 | YBSync.m 84–120 |
| 실패 1건이면 전체 중단, 다시 시작할 때 전체 비교부터 | 재시작마다 수 분 이상 | YBLibrary.m 100 |
| 서버가 문서마다 XML 검증, 본문 검색 추출, R2 저장, D1 왕복 3번 | 무료 요금제라면 CPU 10ms 한도에 걸려 실패할 수 있음(확인 필요) | documents.mjs 20–31, 76–96 |

KB 단위 파일인데도 오래 걸린 것은 전송량 때문이 아니다. **문서마다 붙는 고정비**(대기, 새 연결, 상태 파일 전체 재기록, 폴더 전체 훑기)가 2,900번 곱해졌기 때문이다.

#### 새 방식 — 초기 구축은 별도 업로더로

초기 구축 때 한 번 쓰는 일이므로 Sync 앱과 분리한 **단독 업로더** `bulk-upload.mjs`(Node 하나로 실행, 의존성 없음)를 만들었다. 집 Windows PC에서 Mac 문서 폴더 사본을 대상으로 돌리는 것을 권한다. 구형 Mac의 CPU·회선을 쓰지 않는다.

1. 폴더를 한 번만 읽어 `.pro6` 목록을 만든다. 정렬·해시·XML 파싱은 하지 않는다. `._` 파일은 뺀다.
2. 입장 쿠키 하나로 연결을 유지하고, 동시에 4개씩 **연속 큐**로 POST한다. 자리가 비면 바로 다음 파일을 넣는다.
3. 서버 응답으로 분류한다: 201 새로 올림 / 200 같은 내용(이미 있음) / 409 다른 내용이 이미 있음(덮지 않음) / 4xx 거부(이름 규칙 등) / 5xx·네트워크는 간격을 늘려 3번 재시도.
4. 결과를 `upload-log.jsonl`에 한 줄씩 남긴다. 다시 실행하면 끝난 파일은 건너뛰고 실패분만 올린다.
5. 실패 1건이 전체를 멈추지 않는다.
6. 서버 쪽 변경은 없다. 기존 `POST /api/documents` 그대로 쓴다. 다 끝난 뒤 Sync 2.0의 처음 연결(9.2)이 manifest로 대조하면 전부 "같음"으로 영수증에 들어간다.

Mac에서 직접 돌려야 한다면 같은 스크립트를 Mac의 Node로 돌리거나, Node가 없으면 curl + 셸로 같은 규칙을 옮긴다. High Sierra에는 curl이 있다.

**예상 소요**(추정, 실측 필요)
- 남은 약 2,575개: 서버 처리가 문서당 0.5~1초면 동시 4개로 5~11분이다. 서버의 문서당 처리(XML 검증·본문 추출·R2·D1)가 병목이면 동시 수를 늘려도 안 줄어든다. 첫 실행에서 개/초를 기록해 확인한다.

**ZIP 일괄 업로드는 권하지 않는다.** R2에 ZIP 하나를 올려도, 무료 요금제의 호출당 쿼리·서브요청 50개, CPU 10ms 한도 때문에 서버가 한 번에 풀지 못한다. 잘게 나눠 처리해야 하므로 결국 연속 큐와 비슷해지고, 구조만 복잡해진다. 위 방식으로 실측한 뒤에도 느릴 때만 다시 검토한다.

## 7.6 검색을 D1 부담 없이 하는 방법

**지금 검색이 비싼 이유.** 검색 한 번이 문서 표 전체와 본문 색인 표를 UNION으로 훑는다(`library-catalog.mjs`). 3,107개 합성 자료에서 검색 1회 6,236~12,449행 읽기로 측정돼 있다. 자동 검사가 운영 D1을 치면 하루 500만 행은 몇백 번 검색이면 넘는다.

**방식: 검색 색인 파일 하나를 브라우저가 들고 검색한다.**
- 서버는 문서마다 `[id, 경로, 카테고리, 최근 사용일, 슬라이드 수, 본문 정규화 글자]` 한 줄을 모은 **색인 파일**(JSON, gzip)을 R2에 둔다. 2,900개 × 수백 바이트 = 약 1MB, 압축하면 200~300KB(추정).
- Studio는 입장할 때 한 번 받고(ETag로 바뀐 경우만 다시 받음), 검색은 메모리에서 한다. **검색 1회의 D1 읽기는 0행**이다. 글자 하나 칠 때마다 결과가 바뀌어도 서버에 가지 않는다.
- 이름·본문 모두 부분 문자열 검색이 되고, 결과에 최근 사용일·카테고리·슬라이드 수를 같이 보여 줄 수 있다. 정렬도 브라우저가 한다.
- 색인 파일은 문서를 저장·업로드할 때마다 서버가 그 한 줄만 바꿔 다시 쓴다(R2 읽기 1 + 쓰기 1, D1 쓰기 0). 초기 구축처럼 수천 건이 들어올 때는 저장마다 다시 쓰지 않고, 업로더가 끝났을 때 한 번 다시 만든다.
- 접근 보호: 색인 파일도 세션을 확인하는 Worker 경로로만 준다(지금 `/resources/*`와 같은 방식). 본문 글자가 들어 있으므로 공개 정적 자원으로 두지 않는다.
- 슬라이드 수와 사용일은 업로드 때 서버가 XML에서 센다. 장부만 있는 문서는 Mac이 처음 연결할 때 파일을 한 번 읽으면서 같이 세어 보낸다(어차피 그때 전체를 읽는다).

**대안으로 검토한 것**
- D1 FTS5 전문 색인: 읽는 행은 줄지만, 한글 두 글자 검색은 trigram 토크나이저가 놓치고 D1의 FTS5 지원 범위를 확인해야 한다. 색인 파일 방식이 더 단순하고 비용이 0에 가깝다.
- 지금처럼 D1 검색을 유지하고 색인만 추가: 행 읽기가 줄긴 하지만 검색마다 D1에 간다.

**자동 검사가 운영 D1을 치지 않게**: 검사는 로컬 Worker 모사(이미 있는 `npm test` 구조)만 쓰고, 운영 주소로 가는 검사는 사람이 명시적으로 돌리는 스모크 1~2개로 제한한다. 운영용 바인딩을 검사 환경 변수에서 뺀다.

## 7.7 버전은 문서와 예배 둘 다 매긴다

사용자 질문: "버전을 문서 단위로 매길지 재생목록 단위로 매길지."

- **문서 버전**: 지금처럼 문서마다. 기도·말씀처럼 내용이 바뀌는 것을 잡는다.
- **예배(노드) 버전**: 재생목록 파일 전체가 아니라 예배 하나마다. 순서가 바뀌는 것을 잡는다.
- **예배의 장부(manifest)** = 예배 버전 + 그 예배가 가리키는 문서들의 (id, 버전) 목록. 서버의 plan이 이미 이 모양이다.

사용자의 생각대로 **주로 오가는 것은 재생목록**이고, Sync가 비교하는 단위도 예배의 장부다. 다만 장부 안에 문서 버전 번호가 들어 있으므로, 순서는 그대로인데 기도 내용만 바뀐 경우도 "주일예배말씀 v2 → v3"로 장부 비교만으로 드러난다. 내용을 열어 볼 필요가 없다.

- Mac 영수증의 `nodes` 표가 바로 이 장부의 사본이다. 서버 장부와 Mac 영수증을 예배별로 맞대 "순서 바뀜 / 문서 n개 바뀜 / 같음"을 낸다.
- 양쪽 다 **번호만 비교**한다. 해시 계산은 여기에 없다.

**해시가 느린가.** 아니다. 30KB 문서의 SHA-256은 0.1ms 정도이고, 2,900개 전체(약 80MB)도 구형 Mac에서 수 초다. 지금 느린 것은 해시가 아니라 파일 하나마다 폴더 전체를 다시 읽는 것, 상태 파일 전체를 매번 다시 쓰는 것, 서버 왕복 80회다. 재설계에서 해시는 ① 처음 연결 때 한 번, ② 수정시각이 바뀐 파일(한 주 수십 개)에만 쓴다. 평소 실행에서는 해시가 거의 돌지 않는다.

**Mac 영수증(로컬 장부)의 형태.** SQLite 파일 하나(`receipt.sqlite`). macOS에 내장된 라이브러리라 설치할 것이 없다. 내용은 세 표다.
- `docs`: 파일마다 한 줄 — 경로, 크기, 수정시각, 받은 서버 버전, 쓴 바이트 sha
- `nodes`: 예배마다 한 줄 — 예배 id, 받은 예배 버전, 그때의 문서 (id, 버전) 목록
- `meta`: 받은 마지막 일지 번호, 마지막 적용 회차
파일 전체를 다시 쓰는 일이 없고, 한 줄만 고친다. 사용자가 열어 볼 일은 없다.

- 컨트롤은 지금 쓰는 기본 AppKit만 쓴다(NSTableView, NSButton, NSTextField, NSProgressIndicator). High Sierra 제약 문서를 따른다.

## 9. 고장·복구와 전환

### 9.1 고장과 복구

- **적용 도중 꺼졌을 때:** 다음 실행 때 회차 기록을 보고 **끝까지 마무리**한다. 준비한 파일은 이미 sha를 확인한 서버본이라 앞으로 진행하는 편이 안전하다. 그 사이 사용자가 고친 파일만 건드리지 않고 보류로 남긴다. 앱 전체를 잠그고 사람에게 복구를 요구하지 않는다(A3 해소).
- **되돌리기:** 마지막 회차의 백업을 제자리로 이름 바꾸고 영수증을 회차 이전으로 돌린다. 적용 뒤에 PP6에서 고친 파일(지금 sha가 회차에 쓴 sha와 다른 파일)은 되돌리지 않고 알린다. 서버는 그대로이므로 다음 동기화 때 다시 "받을 것"으로 나온다.
- **영수증이 없어지거나 깨졌을 때:** 메뉴의 전체 검사가 9.2의 2번과 같은 방식으로 다시 만든다. 장치 id는 바뀌지 않는다.

### 9.2 지금 상태에서 넘어가기 (한 번만)

전제(2026-10-04 운영 사이트와 사용자 확인)
- 서버는 10-03에 비우고 정리본 Mac에서 다시 채웠다. 장부 2,884개, 원본 309개, `기본 .pro6pl` v10(활성 8개, 보관 7개).
- 서버 원본 309개는 모두 이 Mac에서 올라갔다. 그중 웹에서 고친 것은 소수다(1부기도·주일예배말씀·2부 기도 v2 등). 서버 재생목록은 웹 편집본이 최신이다.
- Mac 문서 폴더는 정리본 그대로다. 0.6.6의 `state.json`은 참고하지 않는다. 옛 기준이 필요 없을 만큼 상태가 단순하다.

**서버 편집본을 지키는 것이 최우선이다.**

**0. 즉시 할 안전장치** (새 앱보다 먼저)
- 서버가 Sync 0.6.6의 재생목록 파일 전체 PUT을 거절하게 한다(A1 차단). 0.6.6을 켜기만 해도 자동 PUT이 일어날 수 있으므로, 새 앱 전까지 0.6.6으로 재생목록 비교를 하지 않는다.
- 0.6.6에서 "Mac 내용 사용…"·"서버 다시 맞추기"를 쓰지 않는다(A5).

**1. 서버**
- `sync_log`, 장치, 이미지 경로표, 보관본 표를 만든다. 장부와 문서 표를 한 줄로 합친다(5.2).
- 현재 문서·노드·이미지마다 일지 한 줄을 채운다. 노드 이력 표에 아직 없는 노드는 현재 XML로 첫 버전을 만든다. 유한한 작업이고 끝나면 멈춘다.
- plan의 `ready`에서 `missing`을 뺀다. 원본 없는 참조는 항목 표시로만 남긴다.

**2. 교회 Mac, 첫 실행 "처음 연결"**
- 시작 전에 문서 폴더와 재생목록 파일을 통째로 한 번 복사해 둔다.
- 문서 2,884개를 한 번 전부 해시한다. 이번 한 번뿐이다. 50개씩 manifest로 서버와 대조한다(7.5).
  - 같음(309개 대부분) → 영수증에 적는다.
  - 서버에 원본이 없음(약 2,575개) → 장부 이름이 Mac 파일과 맞는지 확인하고, 우선순위대로 올리기 큐에 넣는다.
  - 다름(웹에서 고친 소수) → 서버본을 받는다. Mac 바이트는 안전망대로 보관본으로 남긴다.
- 재생목록 노드는 서버 노드와 Mac 노드의 의미 지문을 비교한다. 다르면 **서버 적용**이고 Mac 노드는 보관본으로 남긴다. 10-03 웹 편집(1부·2부·청년예배)이 이때 Mac에 들어간다. 장부 이름으로 넣은 찬양 4곡은 Mac 파일이 있으므로 그대로 열린다.
- 확인 목록을 한 화면에 보여 주고 "적용"을 받는다. 그 뒤로는 평소 흐름이다.

**2'. 이미지 (집 PC에서, 문서 업로드와 별개로 한 번)**
- 교회 Mac에서 문서 폴더와 `Renewed Vision Media/Images`, `…/ImportedImages` 두 폴더를 그대로 복사해 온다(`YebaeOn/`은 아직 없고, 서버가 채우는 폴더라 복사 대상이 아니다). 폴더 구조와 파일명(NFD 포함)을 바꾸지 않는다. PasteBoardImages·영상·오디오는 가져오지 않는다.

**3. 마무리**
- 0.6.6 앱과 프로필 폴더는 지우지 않고 보관한다.

## 13. Mac ↔ 서버 관리 기준 (2026-10-04 결정)

토론 뒤 사용자가 정한 규칙이다. 위 장과 다르면 이 장이 우선한다.

### 13.1 큰 원칙

- Mac 파일을 바꾸는 일(받기·노드 빼기·문서 이름 바꾸기·macOS 휴지통)은 사용자가 데일리 창에서 [적용]을 눌렀을 때만 한다. 상주 확인은 비교해 보여 주기까지만 한다(2차의 "PP6가 꺼져 있으면 자동 적용"은 없앴다).
- 자동으로 하는 것은 서버에 **더하는** 일뿐이다: PP6를 닫을 때 Mac에서 고친 문서·순서·사용일, Mac 새 문서, 그 문서가 가리키는 허용 폴더의 새 이미지, PP6에서 만든 예배(서버에 없을 때만 추가).
- 없어진 것을 보고 추측해서 지우지 않는다. Mac이 따르는 삭제는 서버 일지의 `trashed`·`renamed`와 서버 휴지통 상태뿐이고, 서버 휴지통으로 보내는 것은 정리 창 버튼뿐이다.

### 13.2 보관함과 휴지통

- 보관(`archived`)은 Mac과 연결되지 않는다. Mac 줄에 "서버에서 보관됨"만 붙는다.
- 휴지통(`trashed`)만 Mac과 연결된다. 예배는 [적용] 때 `.pro6pl`에서 그 노드만 빼고, 문서는 macOS 휴지통으로 옮긴다. Mac 파일이 서버가 알던 내용 그대로일 때만이며, 다르면 두고 정리 창으로 보낸다. Mac 예배가 아직 가리키는 문서는 옮기지 않는다.
- 진짜 삭제는 Studio 휴지통 비우기(관리자)뿐이다. 사용 중·보관함 예배가 가리키는 문서는 비우지 않는다. 휴지통 예배만 가리키는 문서는 비울 수 있고, 그러면 그 예배는 꺼낼 수 없다.
- Mac에서 지운 예배는 되살리지 않는다: 데일리 창에 "Mac에서 삭제한 재생목록"으로 기본 체크 꺼짐. 서버에 새로 생긴 예배는 기본 체크 켜짐.

### 13.3 이름

- 문서 이름 바꾸기: Studio → 일지 `renamed`(id 유지) → Mac [적용] 때 파일 이름과 모든 예배의 cue(경로·이름)를 고친다. Mac → 서버는 sha가 완전히 같은 "옛 경로 사라짐 + 새 경로 생김"만 자동(정리 창 단계).
- 예배 이름은 노드 교체로 양방향이다: 서버 노드가 바뀌었으면 서버 이름을 받고, 서버가 그대로면 Mac 이름을 올린다.
- 이름 겹침(같은 경로, 다른 내용, 영수증이 본 적 없음)은 Sync가 스스로 풀지 않는다. 정리 창에서 [번호 붙여 둘 다 두기]. Studio는 새 문서 이름이 있으면 `이름 2`를 제안한다.

### 13.4 장부와 확인 주기

- Mac 영수증에 장부 사본(`ledger`: 경로 → id·버전·sha·상태, `media`: 이미지 경로 → sha)을 둔다. 처음 한 번 R2 장부 파일(`GET /api/sync/ledger`)로 만들고 그 뒤는 일지로만 고친다. 지운 줄 대신 상태(trashed·purged·renamed)로 남겨 "서버에 있었던 경로"를 잊지 않는다. 새 문서 = 장부 사본과 영수증 어디에도 없는 Mac 경로.
- 상주 15분: 일지 확인 → 관련 예배만 비교·표시. 시작 때: 같음 + 지난 전체 확인에서 7일 지났으면 전체 확인(디스크 대조·외부 참조·이미지 보충 후보, 정리 창 단계). PP6 종료: 올리기.
- 일지의 문서 `trashed`·`renamed`는 영수증 `pending`에 쌓았다가 [적용] 때 실행하고 지운다. `untrashed`는 대기 중인 휴지통을 취소한다.

### 13.5 권한

- 되돌릴 수 있는 일(보관·휴지통 넣기·꺼내기·이름 바꾸기·카테고리 추가)은 누구나, 되돌릴 수 없는 일(휴지통 비우기·카테고리 설정 변경·보관본 해결·고아 이미지 정리)은 관리자(`ADMIN_PASSWORD`, 15분 서명 쿠키)만.
- 동시 편집은 잠그지 않는다. 열 때 "OO님이 n분 전부터 편집 중" 한 줄을 보여 주고, 늦게 저장한 쪽의 409에서는 초안을 버리지 않는다.
